# 工作人员端分工清单（人读版）

> 写给：大二学生（你和队友）
> 同内容的 AI 版：`工作人员端分工清单-ai.md`
> 功能细节以 `工作人员端清单.md` 为准，**这份只管「谁做什么、怎么配合」**
> 三份文件已放进仓库 `design/staff-console/`，队友直接从 GitHub 取
> 日期：2026-10-09 ｜ 截止：2026-10-14（下周三）交一版能演的 demo

---

## 1. 一句话方案

**先一个人花半天把「公共骨架」搭好，然后两人各领一半模块并行开发，每天晚上合并一次，最后一天合练 demo。**

为什么这么分？两个人（外加两个 AI）同时写代码，最容易死的不是写不完，而是**写重了、写岔了**——同一个文件你改一版我改一版，合并时两边对不上。所以先立骨架、划地盘、定规矩，再开工。

---

## 2. 两个岗位

| | **甲（你）** | **乙（队友）** |
|---|---|---|
| 模块 | **工单中心 + 审批中心** | **客户查询 + 代客办理 + 审计日志** |
| 前端 | 工单列表/详情/对话区、审批列表/裁决 | 客户搜索/360 页/流水表、代客办理表单、审计表格 |
| 后端 | tickets/approvals 两张表 + 对应接口 | customers 查询、代客 action 白名单、audit_logs |
| 额外职责 | **给 agent 的 5 个接口**（跟工单/审批长在一起） | `writeAudit()` 帮手（两人共用） |
| 大约占比 | 55% | 45% |

**为什么这么分**：
- 你这条线是 demo 的**脊柱**（客户转人工 → 员工接单 → 主管审批），出问题了必须有人顶，我和你一起扛。
- 队友那条线边界清楚、大量复用客户端现成接口，属于「照方抓药」，适合快速铺开。
- agent 的 5 个接口天然长在工单和审批上，放你这边最顺，不用跨人对齐。

---

## 3. 分三个阶段走

**先插一个硬性前提（M0，10-10 前）**：转账挂起方案要拿到**书面答复**——谁改客户端、阈值取多少。demo 脊柱卡在这几行字上，不许拖到骨架之后。（队友提的，对。）

**M0 兜底（不许死等）**：10-10 晚还没回复？**默认方案自动生效**——客户端那几行由甲按功能清单 §9.3 自己改（改前群里报备一句）；agent 接口按冻结稿直接开工。等回复不是开工的前提。

### 阶段一：搭骨架（半天，**只有甲做**，乙不空等，领三件并行任务）

要产出七样东西：

1. **前端骨架** `staff/`：登录页、左侧菜单、页面布局、配色 token
2. **契约文件** `contract.ts` + 类型定义：员工端所有接口的「形状」先写死（角色枚举用 `csr`/`supervisor`，不叫 `agent`，免得和 AI agent 撞名）
3. **公共 HTTP 请求封装**：`staff/src/api/http/` 里一个统一的 `request()`（带 token、统一错误处理、统一 `{ message, code }` 解析）。**两人都只准调用它，不准各写各的 fetch**——这是队友提的，提得对。
4. **mock 最小版**：每个接口返回一份写死的样例数据就行，**页面不白屏即可**，不要做完整业务模拟（那是假的完备，浪费半天）
5. **后端空壳**：员工表、鉴权中间件（检查登录和角色）、`writeAudit()`、`/staff-api/*` 路由架子
6. **冻结 agent 接口**：把 §5 那 5 个接口的地址和请求体**发到群里定稿**（含「审批通过后钱的动作归服务端」这条）
7. **部署/代理方案**（一页文档写清楚，demo 当天不折腾）：
   - 本地同时跑：客户端 `app/`（5173）+ 员工端 `staff/`（另一个端口，如 5174）+ 后端 `server/`（8080）；员工端的请求代理到 8080
   - 上线 nginx：员工端独立一个站点（如 `staff.waveflow.cn`），照抄客户端那份 nginx 配置的写法；API 走 `/staff-api` 反代到同一个 `server/`
   - 两个前端页面在浏览器开两个标签页，就是 demo 演示形态（客户视角 + 员工视角并排）

**乙在这半天的并行任务**（不许干等）：
1. 精读 `app/src/api/mock/` 里客户/流水/卡的业务规则（后面代客办理要复用）
2. 写三条冒烟脚本骨架：列表渲染 / 状态流转 / 审计落库
3. 备演示种子数据：2 个员工账号、1 张待接工单、1 张待审单、客户聊天样例

> 通俗地说：骨架 = 毛坯房的水电和承重墙。后面两人是往不同房间里搬家具，谁也不能动承重墙。

**阶段一做完的判断标准**：乙能打开前端看到菜单和登录页；`/staff-api/health` 能访问。

### 阶段二：并行开发（约 2.5 天，两人同时干）

| | 甲 | 乙 |
|---|---|---|
| 第 1 步 | 工单中心界面（先用假数据跑通） | 客户查询界面（先用假数据跑通） |
| 第 2 步 | 工单后端接口 | 客户查询后端接口 |
| 第 3 步 | 审批中心界面 + 后端 | 代客办理 + 审计日志 |
| 随时 | 跟接 agent 的队友对齐联调 | 帮甲盯一下契约有没有走样 |

**每天收工前**：两人把代码合到一起，跑一遍主要页面。看见红的当天解决，不许过夜。

### 阶段三：合练（最后 1 天，两人一起）

- 按 demo 脚本走全流程（见第 6 节）
- 补漏、改文案、写演示账号
- 谁上台谁主讲，另一人负责在电脑上切页面

## 4. 地盘划分（最重要的一条）

**原则：下面标了「谁的」目录，就只有谁能改。要动别人的，先在群里说。**

| 位置 | 归谁 | 内容 |
|---|---|---|
| `staff/src/pages/tickets/`、`staff/src/pages/approvals/` | 甲 | 工单、审批的界面 |
| `staff/src/pages/customers/`、`staff/src/pages/actions/`、`staff/src/pages/audit/` | 乙 | 客户查询、代客、审计的界面 |
| `staff/src/api/contract.ts`、`types.ts` | **甲锁管**（乙提需求，甲来改） | 接口形状，全项目的法律 |
| `staff/src/api/http/` 公共请求封装 | 甲建，**两人共用不各写** | 阶段一产物 |
| `staff/src/layout/`、`login`、路由表 | 甲（骨架产物，改动打招呼） | 公共骨架 |
| `server/` 里 tickets/approvals/转账挂起 相关 | 甲 | 工单审批后端（含 §9 大额挂起） |
| `server/` 里 customers/actions/audit 相关 | 乙 | 其余后端 |
| `server/` 的鉴权中间件、`writeAudit()`、建表 | 甲建，**两人共用不动** | 公共地基 |
| `app/**`（客户端） | 原则上不动；**转账审核文案例外** | 见下 |

**关于客户端（`app/**`）**：原来说好双方禁改，但「转账挂起」演示必须让客户 App 显示「审核中 → 放行」（详见 `工作人员端清单.md` §9）。规则改为：**可以小改，但改动前群里报备、改完知会客户端作者**。目前估的量很小（结果页文案分支 + 流水标签，< 30 行），由甲顺手做；客户端作者有空的话也可以认领，认领了甲就不碰。

**通俗地说**：公共文件（契约、登录、建表）只有「一个管家」，别人要改先开口。这是防止合并地狱的关键。

## 5. 三条军规 + Git 规矩

1. **契约先行，改形状先报备**
   `contract.ts` 定了就是法律。谁想加字段、改错误码，先发消息说一声，改的人统一是甲。
   （你们队友在客户端那边就是这么干的，效果很好，接着用。）

2. **每天合并一次，不许攒**
   每天收工把两人的改动合到一起跑一遍。**最经典的死法是周三晚上才第一次合并。**

3. **AI 各自干活可以，公共文件不许各写各的**
   你和队友都用 AI 没问题，但让 AI 改 `contract.ts`、鉴权、建表之前，**先确认对方今天有没有动过**。

**Git 规矩（一句话写死，照做）**：各自开分支开发（`feat/staff-a-xxx` / `feat/staff-b-xxx`），**每天合并前先 pull**，冲突当场解；**契约改动单独一个 commit，标题带 `[contract]` 前缀**，别的代码不混进这个 commit。

## 6. Demo 脚本（最后照这个演）

1. 客户在 App **真的提交一笔 8000 转账**（在转账页操作，不是聊天里说说）→ 超阈值，App 显示「**审核中**」，审批中心自动出现待审单
2. 客户再对 Agent 说「我刚转的那笔不太放心，找人工」→ **切员工端**：工作台冒出新工单（3 秒轮询），点开看到 Agent 聊天记录，工单挂着那笔转账的单号
3. **切主管身份**点通过 → 服务端放行执行
4. 员工接手工单 → 客户查询看一眼流水 → 在工单里回复「已加急处理」
5. 回 App：客户刷新，看到 8000 从「审核中」变成**放行成功**（少于阈值的转账则完全无感，不用审）
6. （有余力）主管打开审计日志：刚才每一步都有记录

> 为什么第 1 步必须真提交：聊天只会建工单，不会产生挂起转账和审批单。聊天文本不能当支付指令。

**翻车兜底**：演示前跑 `tools/reset-demo.mjs` 归零；合练时录屏，现场挂了放视频。有一个额外的失败故事可以备着：审批通过时钱已经被花光 → 放行失败，工单里自动有一条跟进记录（证明系统真的在把关，不是演的）。

每一步落在谁的模块上：①②③④ 一半是甲的（工单+审批），④的客户查询和⑥审计是乙的。**所以两人必须合练，不能各演各的。**

## 7. 验收自查（周三上午跑一遍）

- [ ] 两个角色登录后菜单不一样；直接输主管页面的网址会被拒
- [ ] agent 打接口建一张工单，员工端列表**看得到**
- [ ] 审批单只许裁决一次；驳回不写理由会被拦住
- [ ] 查看客户完整信息后，审计里有一条记录
- [ ] 代客锁卡之后，客户端那张卡**真的锁了**（两边是同一份数据）
- [ ] 审批通过时钱已被花光 → 放行失败、工单里有自动跟进记录
- [ ] **演示/合练前确认客户端 `VITE_USE_MOCK=false` 连着真后端**（mock 是立即到账，挂起链只有真后端有）
- [ ] 后端没启动时，前端不白屏（给一句人话提示）

## 8. 降级预案（万一时间不够）

按这个顺序砍，**不要砍前两项**：

| 顺序 | 砍什么 | 后果 |
|---|---|---|
| 1 | 风控告警（本来就 P2） | 无感 |
| 2 | 代客办理只留「锁卡」一个动作 | 演示够用 |
| 3 | 审计只记不查（表格页可以不做） | 后补 |
| — | **工单、审批、客户查询** | **砍了 demo 就演不了，不许动** |
