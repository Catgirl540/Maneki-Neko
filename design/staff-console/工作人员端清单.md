## 2. 模块清单（按优先级）

## 4. 状态机（后端必须钉死，前端照着渲染）

### 4.1 工单 `status`

```
open（待处理）→ processing（处理中）→ waiting（等客户）⇄ processing
                              ↘ resolved（已解决）
open / processing → suspended（挂起）→ processing
```
- `open → processing` 需要 `assignee`（接手）
- 终态 `resolved` 不可再改
- 非法流转直接 400，错误文案写清楚

### 4.2 处置 `status`

**transfer 类（延迟到账 + 拦截窗口，§9）**
```
pending → settled     （窗口到点自动到账 / 员工「立即到账」）
pending → intercepted （员工拦截，必带枚举理由）
pending → recalled    （客户撤销）
```

**非 transfer 类（锁卡 / 调额…，仍是审批语义）**
```
pending → approved   （主管点通过）
pending → rejected   （主管点驳回，必填理由）
```
- **一次性**：已收口再处置 → 409
- `pending` 超时策略：transfer 类靠自动到账扫账收口（§9.5），demo 不做人工催办

## 5. Agent 对接面（★ 给队友的接口约定）

> 原则：agent 把员工端当**普通 HTTP 服务**用。全部走 `POST/GET`，JSON 进出。
> 下面 5 个就是全部；多一个都算我没设计好。

### 5.1 转人工

```http
POST /staff-api/tickets
{
  "customerId": "u_0001",
  "channel": "app" | "im" | "web",
  "reason": "客户要求转人工",
  "transcript": [ { "role": "user"|"assistant", "text": "…" } ],
  "priority": "normal" | "high"
}
→ 201 { "ticketId": "T-...", "status": "open" }
```

### 5.2 提审敏感操作

```http
POST /staff-api/approvals
{
  "customerId": "u_0001",
  "bizType": "transfer" | "card_lock" | "limit_adjust" | "wealth_subscribe" | "other",
  "transferId": "txn_... | null",   // bizType=transfer 时必填，必须指向已挂起指令
  "ticketId": "T-... | null",       // 可选，关联工单
  "payload": { "…": "非 transfer 类的业务参数" }
}
→ 201 { "approvalId": "A-...", "status": "pending" }
```

**转账类提审防伪造（2026-10-09 第三方评审采纳）**：
- `bizType='transfer'` 的审批**只能由服务端已挂起的转账指令生成**。agent 不得自述金额/收款方/riskSummary——后端从指令表自行读取金额、账户、收款方，自动生成风险摘要。
- **唯一约束**：一笔转账指令同时只允许一张 `pending` 审批单；重复提审返回原单（幂等）。
- 非 transfer 类（锁卡/调额/理财）仍可带 `payload`，但 `riskSummary` 后端不采信 agent 自述，自行生成。

### 5.3 查裁决结果（长轮询或轮询都行）

```http
GET /staff-api/approvals/:id
→ 200 { "status": "pending"|"approved"|"rejected", "reason": "…" }
```

### 5.4 查工单状态

```http
GET /staff-api/tickets/:id
→ 200 { "status": "open"|"processing"|"resolved"|"…", "messages": [...] }
```

### 5.5 员工对话回写（**P0**，demo 第 4 步要用）

```http
POST /staff-api/tickets/:id/messages
{ "text": "…" }        // sender 由服务端按登录态生成，请求体不带、带了也不信
```

**给队友的约定**
1. 鉴权：调用方带 `X-Agent-Token: <shared-secret>`（demo 一个固定值即可；token 放环境变量，不进代码）
2. 所有接口幂等重试安全：`approvalId`/`ticketId` 由我方生成，队友重复 POST 不产生重复单（用 `Idempotency-Key` 请求头或客户端生成 uuid）
3. 我方保证：这些接口**不需要员工登录态**，走 agent 专用通道；员工前端走另一套 token
4. 错误体沿用客户端风格：`{ "message": "中文文案", "code": "..." }`
5. **资金闭环职责（2026-10-09 钉死，xpy 提出；2026-10-10 随延迟到账改写）**：处置后的**钱动作归服务端收口**，不归 agent——窗口到点自动到账，或主管点拦截/立即到账 → 服务端对那张在途转账单做解冻/扣款结算。agent 的活是提审、轮询 `GET /approvals/:id`、把结果**通报**给客户/工单，**禁止再调一次转账接口**（防双重执行）。员工端也永不发起新转账，只拦截/提前到账。
6. **agent 与员工分权（第三方评审采纳）**：两类调用方共用业务服务，但**不共用权限面**。agent token 仅可：建单、查**自己创建的**单、回写允许的消息；员工 token 才能接单/转派/发员工消息。`sender` 一律由服务端从登录态生成，**不信任请求体**。

**Demo 流程（照这个演）**：
1. 客户在 App **真的提交一笔 ¥8,000 转账**（转账页操作，不靠聊天触发）→ 超阈值（默认 ¥500,000，可在处置中心现场调低到 ¥5,000 便于演），App 立刻显示「**转账处理中 · 还剩 X 秒**」+ 撤销按钮，处置中心自动出现在途单（带倒计时）
2. 客户在 Agent 会话里说「我刚转的那笔 8000 不太放心，帮我找人工」→ **切员工端**：工作台冒出新工单（前端 3 秒轮询），点开看到 Agent 聊天记录，工单带 `transferId` 串起那笔转账
3. 处置中心打开那张「大额转账」在途单 → 主管身份点「**拦截**」→ 选枚举理由（如「疑似诈骗」）→ 本金退回客户可用余额
4. 员工接手工单 → 客户查询看一眼这个客户流水 → 在工单里回复「已为您拦截，资金已退回」
5. 回到 App：客户看到那笔 8000 变为「已拦截」，可用余额回来了
6. （对照）再转一笔大额，**什么都不做** → 窗口到点自动到账，处置中心自己变成「已到账」
7. （有余力）主管打开审计日志：刚才每一步都在

> **为什么第 1 步必须真提交**：聊天文本只会建工单，不会产生在途转账和处置单。若想让聊天直接发起转账，须另设计客户确认与核验流程——聊天/语音文本本身**不能**当支付指令（红线）。转账指令和工单靠 `transferId` 串成一条业务链。
>
> **演示提示**：demo 把窗口调成 30 秒（`BANK_TRANSFER_HOLD_SECONDS=30`），够演完拦截；要演「自动到账」就再转一笔等 30 秒。合练时确认客户端是 `VITE_USE_MOCK=false` 连真后端——mock 里默认不带阈值是立即到账的。

**翻车兜底**：演示前跑 `tools/reset-demo.mjs` 重置数据；合练时录屏，现场网络挂了放视频。

## 9. 大额转账：延迟到账 + 拦截窗口（2026-10-10 重设计，demo 主线）

> **模型换成「刹车」不是「闸门」**（用户 2026-10-10 拍板）。旧的「主管审核放行」把客户的转账权交到了员工手上——用户点确认，钱却要等员工点头，这不合理。新模型：**默认到点自动到账**，员工只有**时间窗内的一票否决（拦截）**，且拦截必须给枚举理由。对应现实里的「延时到账 + 紧急止付」。

### 9.1 产品规则（已拍板）

- **设定金额以下**：无感完成，客户端照旧立即到账。
- **设定金额及以上**：进入**在途**（延迟到账）→ 客户点确认后起算一个窗口（默认 5 分钟，demo 调 30 秒）→ **窗口到点自动到账，无需任何人放行**。
- 窗口内可做的事，只有三种，全是**否决/撤销**，没有「批准」：
  1. **员工拦截**（一票否决）：必须从枚举里选理由 —— `疑似诈骗` / `收款方风险名单` / `交易行为异常` / `客户来电要求叫停`。**不收自由文本**，自由文本等于允许「看着不爽」这种理由。可选补充说明另存。
  2. **客户撤销**：随时反悔，本金立刻解冻。
  3. **员工「立即到账」**：把剩余窗口时间跳过，马上执行 —— 这是**提前放行**，不是审批，语义上等同于「我不拦」。
- **阈值是运行时配置**（2026-10-12 拍板）：落在 `staff_settings` 表，**员工端随时改、改完立刻对下一笔转账生效、重启不回退**。
  - 默认 **¥500,000 = `50000000` 分**（`BANK_TRANSFER_REVIEW_CENTS` 只作**首次建库的种子值**，不是唯一事实来源）
  - 接口：`GET /staff-api/settings/transfer-threshold`（员工可读）/ `PUT`（**只许主管**，写审计 `settings.transferThreshold.update`）
  - UI：处置中心顶部「延迟到账阈值」面板，主管点「修改」填**元**，落库转**整数分**
  - 校验：必须是正整数分，且 ≤ ¥900,000（须低于单笔转账上限，否则转账根本走不到「进窗口」那一步）
- 窗口时长仍是环境变量，不写死前端：
  - `BANK_TRANSFER_HOLD_SECONDS`，默认 `300`（5 分钟）；demo 演示取 `30`

**为什么这样更合理**：客户的转账权本来就该默认行使。员工的职责是「看出问题时踩一脚刹车」，不是「每个人都要给我看一眼」。刹车有时间上限、有必须记录的理由、有审计——权被关进笼子；闸门没有。

### 9.2 资金怎么锁（钱为什么永远扣得动）

- 提交时**只冻结 `available`（可用余额）中的本金**，不动 `balance`（余额）。
  - 客户立刻看到「可用余额」少了，知道钱被占住了；「余额」不变，知道还没真走。
  - **手续费在真正执行时才计**，冻结只锁本金，避免冻结金额算不准。
- 流水预写一条 `status='pending'`，带 `pendingReason='inflight'` 和 `holdUntil`（窗口截止 ISO 时刻）。
- 因为本金已经锁住，**窗口到点的自动到账永远扣得动** —— 「审批已通过但执行失败（余额被花光）」这条分支在新模型下**不存在**了。这是本次设计最重要的收益。

### 9.3 状态怎么落到现有类型上

客户端已有：
- `TransactionStatus = 'success' | 'pending' | 'failed'`（`pending` 文案=「处理中」，`app/src/lib/tx.ts`）
- `TransferResult.settlementStatus?: 'success' | 'pending'`（外行模拟清算用）

约定：
- **在途中的转账** = 流水 `status: 'pending'`。仍用现有 `'pending'` 承载，**不新增第四种状态**。
- 条目加两个可选字段（本方案的客户端契约改动，走报备 + `[contract]` commit）：
  - `pendingReason?: 'inflight' | 'clearing'` —— `inflight` = 大额延迟到账窗口；`clearing` = 外行模拟清算。**旧值 `'review'` 已废弃**。
  - `holdUntil?: string` —— 窗口截止时刻（ISO），只在 `inflight` 的行上出现。
- **字段谁填**：**服务端填**（甲实现），由稳定业务字段产生，查询时直接读列输出；**禁止**对 `approvals.biz_payload` JSON 做临时关联查询推导。
- 展示：`inflight` 显示「在途·延迟到账」+ 倒计时；到点自动变 `success`（两个字段一起消失）。拦截/撤销 → `failed`，流水 `memo` 里写清是「已拦截：<理由>」还是「已撤销」——客服与客户看到同一句话。
- 金额单位**统一整数分**：¥5,000 = `500000`，文档和代码里不许混用「元」。员工端 UI 输入框填元，只在前端换算一次。

### 9.4 客户端要改什么（已改完，待客户端作者签字）

1. `types.ts` / `contract.ts`：上述两个字段 + 新增 `transferRecall` 路由与 `recallTransfer` 方法。
2. `TransferPage.tsx` 结果区：`inflight` 分支显示「转账处理中 · 还剩 X 秒」+ **撤销**按钮。
3. `TransactionDetailPage.tsx` / `lib/tx.ts`：`inflight` 文案 + 在途截止时刻 + 撤销按钮。
4. `app/src/api/mock/**`：延迟到账业务实现（冻结 / 撤销 / 拦截 / 自动到账），约 150 行 —— **超出「< 30 行」的原估**，因为新模型把整条挂起链搬进了 mock。已在群里报备，**待客户端作者签字**。

### 9.5 后端行为

**红线：不许直接 `UPDATE bank_transactions`。** 现有同步机制（`server/database.mjs` `saveLedger`）每次保存客户档案都会**删除并重建**该客户全部账户与流水——只改流水表，下次同步就被覆盖。所有资金动作必须走共用业务入口（`submitTransfer` + `persist()`）。

正确路径：
1. **共用「执行转账」业务入口**（与客户端 `submitTransfer` 同一条业务路）：扣款 → 入账 → 写档案流水 → 同步 `bank_*` 表。
2. **提交大额 → 进窗口**：冻结本金可用额度；流水预写 `pending` + `pendingReason='inflight'` + `holdUntil`；同时自动创建处置单（`biz_type='transfer'`），`biz_payload` 冻结 `{transactionId, customerId, request, amount, fee, holdUntil}`。**唯一约束**：一笔指令同时只允许一张有效处置单。
3. **三种收口，都走同一个 `settleHeldTransfer`**：
   - `settled`（自动到点 / 员工立即到账）→ 解冻后调共用入口真正扣款入账
   - `intercepted`（员工拦截）→ 只解冻，指令从未执行过，流水翻 `failed`
   - `recalled`（客户撤销）→ 同上
4. **处置结果与资金执行结果分开存**：`approvals.status` 管处置（`pending/settled/intercepted/recalled`，非 transfer 类仍是 `approved/rejected`）；`execution_status` 管资金（`pending/succeeded/failed`）。
5. **自动到账扫账**：服务端每秒扫一次到期的 `inflight` 指令，到点自动 `settled`。窗口粒度要够细，否则倒计时和实际到账对不上。
6. **职责边界**：员工端只有拦截/立即到账，**永不发起新转账**；agent 只提审/轮询/通报，**禁止再调一次转账接口**（防双重执行）。
7. **拦截理由是枚举**，服务端二次校验 `reasonCode ∈ INTERCEPT_REASONS`，自由文本一律 400。
