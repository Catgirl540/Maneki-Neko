## 1. 角色与权限（简化版 RBAC，demo 够用）

只做**两个角色**，不做完整权限系统：

| 角色 | 能干什么 | 演示里谁演 |
|---|---|---|
| **客服专员** `csr` | 接工单、客户查询、代客办理、发对话 | 主要角色 |
| **主管** `supervisor` | 客服的全部 + **审批通过/驳回** + 看审计日志 | 切换身份演一下 |

> 枚举定 `csr`（customer service rep）而不是 `agent`——后者与 AI agent 撞名（xpy 建议，2026-10-09 采纳）。

- 登录页独立于客户登录（员工账号 + 密码）
- 前端菜单按角色显隐；**后端每个接口都校验角色**（不能只藏按钮）
- 员工身份 = `Authorization: Bearer <staff-token>`，与客户 token 不混用

## 4. 状态机（后端必须钉死，前端照着渲染）

### 4.1 工单 `status`

```
open（待处理）→ processing（处理中）→ waiting（等客户）⇄ processing
                              ↘ resolved（已解决）
open / processing → suspended（挂起）→ processing
```
- `open → processing` 需要 `assignee`（接手）
- 终态 `resolved` 不可再改
- 非法流转直接 400，错误文案写清楚

### 4.2 审批 `status`

```
pending → approved   （主管点通过）
pending → rejected   （主管点驳回，必填理由）
```
- **一次性**：已裁决再裁决 → 409
- `pending` 超时策略 demo 不做

## 5. Agent 对接面（★ 给队友的接口约定）

> 原则：agent 把员工端当**普通 HTTP 服务**用。全部走 `POST/GET`，JSON 进出。
> 下面 5 个就是全部；多一个都算我没设计好。

### 5.1 转人工

```http
POST /staff-api/tickets
{
  "customerId": "u_0001",
  "channel": "app" | "im" | "web",
  "reason": "客户要求转人工",
  "transcript": [ { "role": "user"|"assistant", "text": "…" } ],
  "priority": "normal" | "high"
}
→ 201 { "ticketId": "T-...", "status": "open" }
```

### 5.2 提审敏感操作

```http
POST /staff-api/approvals
{
  "customerId": "u_0001",
  "bizType": "transfer" | "card_lock" | "limit_adjust" | "wealth_subscribe" | "other",
  "payload": { "amount": 500000, "payeeName": "梁乐怡", "…": "业务参数原文" },
  "riskSummary": "单笔 5000 元，超过二次确认阈值"
}
→ 201 { "approvalId": "A-...", "status": "pending" }
```

### 5.3 查裁决结果（长轮询或轮询都行）

```http
GET /staff-api/approvals/:id
→ 200 { "status": "pending"|"approved"|"rejected", "reason": "…" }
```

### 5.4 查工单状态

```http
GET /staff-api/tickets/:id
→ 200 { "status": "open"|"processing"|"resolved"|"…", "messages": [...] }
```

### 5.5 员工对话回写（**P0**，demo 第 4 步要用）

```http
POST /staff-api/tickets/:id/messages
{ "sender": "staff", "text": "…" }
```

**给队友的约定**
1. 鉴权：调用方带 `X-Agent-Token: <shared-secret>`（demo 一个固定值即可；token 放环境变量，不进代码）
2. 所有接口幂等重试安全：`approvalId`/`ticketId` 由我方生成，队友重复 POST 不产生重复单（用 `Idempotency-Key` 请求头或客户端生成 uuid）
3. 我方保证：这些接口**不需要员工登录态**，走 agent 专用通道；员工前端走另一套 token
4. 错误体沿用客户端风格：`{ "message": "中文文案", "code": "..." }`
5. **审批闭环职责（2026-10-09 钉死，xpy 提出）**：审批通过后的**钱动作归服务端放行**，不归 agent——主管点通过 → 服务端对那张已挂起的转账单做扣款结算；余额不足 → 单子翻 `failed` 并自动回写一条工单消息。agent 的活是提审、轮询 `GET /approvals/:id`、把结果**通报**给客户/工单，**禁止再调一次转账接口**（防双重执行）。员工端也永不发起新转账，只放行/驳回已挂起指令。

## 9. 转账挂起 / 审核放行（2026-10-09 队友对齐后新增，demo 主线）

### 9.1 产品规则（已拍板）

- **设定金额以下**：无感完成，**不需要审核**，客户端照旧立即到账。
- **设定金额及以上**：进入**审核中**（挂起）→ 主管在审批中心通过 → 客户 App 看到放行。
- 阈值存配置（`server` 侧常量/环境变量），demo 取 **¥5,000**（与客户端现有「单笔 ≥ ¥5,000 二次确认」同一条线，故事好讲）。可调，不写死在前端。

### 9.2 状态怎么落到现有类型上（客户端改动尽量小）

客户端已有：
- `TransactionStatus = 'success' | 'pending' | 'failed'`（`pending` 文案=「处理中」，`app/src/lib/tx.ts`）
- `TransferResult.settlementStatus?: 'success' | 'pending'`（外行模拟清算用）

约定：
- **挂起中的转账** = 流水 `status: 'pending'`。用现有 `'pending'` 承载，**不新增第四种状态**（避免动 `types.ts` 契约）。
- 展示层区分（不进 BankApi 契约）：该笔流水若能关联到一张 `pending` 审批单（`approvals.biz_payload.transactionId`）→ 显示「**审核中 · 等待放行**」，否则维持「处理中」。
- 审批 `approved` 后：流水翻成 `status: 'success'`，客户端刷新即见放行。`rejected` → 翻成 `failed`，附驳回理由。

### 9.3 客户端谁来改（结论）

**改动量很小，建议由我（员工端负责人）顺手做，但走报备**，因为：
1. 逻辑在「金额 ≥ 阈值 → 不立即成功 → 等审批」，后端/业务层在 `server/` 与 mock 规则，本来就是我这边联调。
2. `app/**` 唯一要动的是**结果页文案分支**（`TransferPage.tsx` 结果区多一个「审核中·等待放行」分支）+ 流水列表状态标签微调。两处合计预计 < 30 行。
3. 备选：写清楚补丁说明发给客户端作者代改。分工清单已把 `app/**` 禁改改为「**改动前群里报备、改完知会**」。

### 9.4 后端行为（员工端后端 + server）

- 转账提交：金额 ≥ 阈值 → **挂单不扣款**，流水 `pending` + **自动创建一张审批单**（`biz_type='transfer'`，`biz_payload.transactionId`）→ 不经 agent，直接进审批中心。
- 审批通过 = **放行执行**：服务端对这张已挂起的单做扣款结算 → 流水 `success`。**余额被花光导致扣款失败** → 流水 `failed` + 自动回写一条工单消息（xpy 的失败故事保留）。
- 审批驳回：流水 `pending → failed`，写审计，理由回传给客户端展示。
- **职责边界**：员工端只对「已挂起指令」放行/驳回，**永不发起新转账**；agent 只提审/轮询/通报，**禁止重复调用转账接口**（防双重执行）。二选一钉死在本条，不许两头都做。
