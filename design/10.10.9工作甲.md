## 一句话结论

**P0 主链已经打通并被 47 项冒烟钉死**，而且模型已经从「闸门」换成「刹车」：
客户转大额 → 本金冻结进在途窗口 → **到点自动到账**（没人管也放行），员工只有窗口内
一票否决（拦截，必选枚举理由），客户随时可撤销。**「审批已通过但执行失败」这条分支
在新模型下不存在了**——本金提前锁住，到账永远扣得动。
剩下的不是「做不出来」，而是**等人**：agent 联调要对方拿冻结稿来对，`app/**` 的改动要客户端作者点头。

## 二、为什么改设计（2026-10-10 你拍板）

旧模型：大额转账挂起，**主管点头才放行**。
问题：客户的转账权被员工收走了——用户自己点的确认，钱却要等一个外人批准，这不合理。

新模型（对应现实里的「延时到账 + 紧急止付」）：

| | 旧（闸门） | 新（刹车） |
|---|---|---|
| 默认行为 | 等员工批准 | **窗口到点自动到账** |
| 员工权限 | 通过 / 驳回 | **只有拦截**（一票否决） |
| 拦截理由 | 自由文本 | **必须选枚举**（疑似诈骗 / 收款方风险名单 / 交易行为异常 / 客户来电要求叫停），自由文本 400 |
| 客户 | 被动等 | **随时可撤销** |
| 资金 | 挂起不扣款，放行时才扣 | **提交时冻结本金**（动 `available` 不动 `balance`） |
| 执行失败 | 可能「批了但没钱」 | **不存在**——钱已经锁住 |

阈值与窗口都是服务端 env，不写死前端：`BANK_TRANSFER_REVIEW_CENTS`（默认 ¥5,000）、
`BANK_TRANSFER_HOLD_SECONDS`（默认 300 秒 = 5 分钟，demo 调 30）。

### 4.1 工作人员端前端 `staff/`

- **骨架**：React 19 · TS · Vite 8 · Tailwind 4 · React Router 7，端口 5181，`/staff-api` 代理到 8080
- **登录/会话**：`LoginPage`（登录后**不自己跳转**，重定向只在 `App.tsx` 做）
  · `SessionProvider` / `RequireAuth` / `RequireSupervisor`
- **工单中心**（A1）：状态/渠道/关键词筛选、3 秒轮询、状态机按钮、「转给主管」= 纯转派
- **处置中心**（A3 + A3.5，原「审批中心」已更名）：
  - 列表 3 秒轮询 + 状态筛选 + **窗口倒计时列**
  - 抽屉里是**冻结的参数快照**（金额/收款人/指令号/窗口截止）
  - **在途窗口**大字倒计时 + 「到点自动到账，无需员工放行」提示
  - **立即到账**（跳过剩余窗口）/ **拦截**（下拉选枚举理由 + 可选补充说明）
  - 非转账类（锁卡/调额）仍是通过 / 驳回
  - 状态标签：在途 / 已到账 / 已拦截 / 用户已撤销
- **契约**：`contract.ts` v1.2 是唯一接口面，mock 与 http 双实现方法集合一致

### 4.2 服务端 `server/staff-api.mjs`

- 六张表：`staff_users` / `staff_sessions` / `tickets` / `ticket_messages` / `approvals` / `audit_logs`（+`customer_access_logs`）
- 员工 token（12h）与客户 token 分离；agent 走 `X-Agent-Token`
- **权限面**：agent 只能建单 / 看自己建的单 / 回允许的消息；`sender`/`actor` 一律服务端生成
- **审计**：所有写操作 `writeAudit()`，记录不可删改
- **处置闭环（§9.5）**：
  - `createTransferApproval` 自动建单，**幂等**，`riskSummary` 服务端生成
  - transfer 类提审只认**已在途的指令**，金额/收款方从指令读 → 防伪造
  - `decide` 只收 `settle` | `intercept`；**拦截必带 `reasonCode` ∈ 枚举**，自由文本 400
  - 走 `bankHooks.settleHeldTransfer`，**不直接改流水表**（红线）
  - `status`（处置结果）与 `execution_status`（资金结果）**分开存**
  - `closeTransferApproval` 统一收口三种结局：`settled` / `intercepted` / `recalled`

### 4.3 资金侧接线

| 文件 | 改动 |
|---|---|

| `framework/bridge/demo-bank.mjs` | `createDemoBank({ reviewThreshold, holdWindowMs, onTransferHeld, onHoldClosed })` + `getHeldTransfer` / `settleHeldTransfer` / `tickHolds()`（跨档案扫到期窗口） |
| `server/database.mjs` | `bank_transactions.pending_reason` 列 + 迁移；导出 `CURRENT_KEY` / `PROFILES_KEY` |
| `app/src/api/mock/index.ts` | 阈值进窗口 + **冻结 `available` 本金** + 占位流水 `pendingReason='inflight'` + `holdUntil` + `heldRequest` 冻结快照 + `recallTransfer` + `settleHeldTransfer` / `settleExpiredHolds` |

**收口的实现方式**（关键设计，别改坏）：三种结局都走同一个 `settleHeldTransfer`——
`settled` = 解冻后用**无阈值**的 `createMockApi()` 实例重新 `submitTransfer(冻结指令)`，
就是同一条业务路，余额校验/台账/收款人簿全部复用，**零复制业务规则**；
`intercepted`/`recalled` = 只解冻，流水翻 `failed`，memo 写明「已拦截：<理由>」/「已撤销」。
