# 招财猫 Bank 安卓客户端安全自评报告

# 1 自评概述

## 1.1 评估对象

本报告只评估 **安卓客户端**（`android-app/`，Kotlin + Jetpack Compose，包名 `com.moneymeow.bank`，报告时版本 1.0.8 / versionCode 9，minSdk 26、targetSdk 36）。银行服务端、员工端网页与三个 Agent 的权限与数据保护由《安全自评报告》单独评估，本报告不重复。

自评日期 2026 年 11 月 2 日。评估方法是先读实际源码，再在真机（HONOR AMG-AN00 / Android 16）与构建产物上核对行为；结论区分「已实现」「已验证」「未实现或存在缺口」三种状态，未核实的部分显式标注。

## 1.2 总体评价

客户端把「身份」交给服务端判定，本地只保存会话令牌，不保存支付密码，也不在本地做任何权限判断。针对移动端最容易出事的三类场景做了专门处理：

1. **第三方输入法读取密码**——金额、账号、手机号、验证码与 6 位支付密码全部改用 App 内自绘键盘，输入不经过系统输入法（`SecureKeypad.kt`）；
2. **截屏与录屏**——密码页与自绘键盘弹层设置 `FLAG_SECURE`（`SecureWindow.kt`）；
3. **资金操作结果未知**——只持久化一个不透明幂等键与操作名，重启后强制先核查上一次结果才能发起新操作（`FinancialRecovery.kt`）。

自评期间发现的 6 项缺口已在同一轮修复：明文流量与系统备份开关关闭、令牌改为 Keystore 加密存储、卡号/安全码与交易详情页加防截屏、更新包增加签名比对、WebView 链接协议加白名单。修复内容与验证结果见第 8、9 章；第 8 章保留问题记录与残余风险，便于复核。

# 2 资产与信任边界

| 资产 | 位置 | 保护手段 | 状态 |
| --- | --- | --- | --- |
| 会话令牌 | 应用私有 SharedPreferences | 仅本应用可读（MODE_PRIVATE）；401 失效 | 已实现，存储未加密（见 8.2） |
| 支付密码 | 仅存在于内存与当次请求体 | 不落盘、不进日志 | 已实现 |
| 卡号与安全码 | 服务端短时下发，内存缓存按到期时间清除 | 到期自动隐藏 | 已实现，未屏蔽截屏（见 8.3） |
| 余额、流水、资料 | 服务端 | 客户端只做展示 | 已实现 |
| 安装包更新通道 | 站点清单 + APK | sha256 校验 + 系统安装器签名校验 | 已实现（见 5.2） |

信任边界有三处需要说明：

- **设备本身不可信**。客户端不假设设备未被 root、未装无障碍服务；因此敏感输入与展示的防护只做「降低旁观与截屏泄露」，不宣称能对抗已 root 的宿主。
- **系统输入法不在信任范围内**。凡是可能被输入法读到的字段，都尽量改走自绘键盘；仍走系统键盘的字段在第 8.4 节列出。
- **更新清单是信任根之一**。清单来自站点 HTTPS，APK 的 sha256 由清单给出，二者同一来源，因此清单本身的完整性依赖 TLS。

# 3 身份与会话安全

## 3.1 登录

登录使用手机号、登录密码与短信验证码三项（`AuthScreens.kt:120-175`），服务端校验后返回令牌。客户端不保存密码，`password` 只存在于 `remember` 状态中，页面销毁即失。

登录密码强度规则在本地与服务端同源（`PasswordPolicy.kt:4-12`：至少 8 位、含大写、小写与特殊字符，UTF-8 不超过 1024 字节）；本地校验只用于即时提示，最终以服务端为准。

## 3.2 令牌保存与失效

令牌与展示用资料存在应用私有的 SharedPreferences（`BankApi.kt:1497-1522`）：

```kotlin
private const val PREFS = "money_meow_session"
private lateinit var prefs: android.content.SharedPreferences
fun init(context: Context) { prefs = context.getSharedPreferences(PREFS, Context.MODE_PRIVATE) }
```

401 的处理有明确例外，避免把「支付密码输错」误判成「登录过期」而清掉会话（`HttpTransport.kt:60-66`）：

```kotlin
val isPaymentPasswordFailure = apiCode == "BAD_PAY_PASSWORD"
if (status == 401 && notifyUnauthorized && !isPaymentPasswordFailure && !path.startsWith("/api/auth/")) {
    BankApi.onUnauthorized?.invoke()
}
```

资金恢复流程重放请求时会带「抓取时刻的旧令牌」，这类调用传 `notifyUnauthorized = false`，不会误清新会话（`HttpTransport.kt:23-24`、`FinancialRecovery.kt:28`）。

## 3.3 调试构建与正式构建

两套构建产物分开：正式包 `com.moneymeow.bank` 不自动登录（`build.gradle.kts:43`），`dev` 变体包名加 `.dev` 后缀、自动登录演示账户（`build.gradle.kts:59-62`），可与正式包并存而不覆盖。**发版必须使用 release 产物**，debug/dev 包不应分发给用户。

# 4 敏感输入与展示

## 4.1 自绘安全键盘

第三方输入法是移动端最直接的明文泄露渠道：输入法进程能看到键入内容，国产 ROM 的「安全键盘」是否触发又取决于厂商策略。客户端的处理是**不使用系统输入法**：

- `SecureNumberPadDialog` 用 Compose 自绘 3×4 数字键盘，全程不唤起 IME（`SecureKeypad.kt:57-140`）；
- 支付密码键位每次打开重新洗牌，肩窥拿到的固定位置不成立（`SecureKeypad.kt:80`）；
- 金额类输入在键盘内部统一规整：一个小数点、最多两位小数、不堆前导零（`SecureKeypad.kt:146-170`），调用方拿到的必是合法值；
- 键盘弹层自身设置 `FLAG_SECURE`（`SecureKeypad.kt:104`）。

覆盖范围：6 位支付密码共 15 处输入点使用 `SecurePinField`（`AuthScreens.kt:573,579`、`CardsScreen.kt:1067,1152`、`MoreScreens.kt:874,1195`、`PaymentPlansScreen.kt:265,280`、`ProductDetail.kt:401`、`SavingsPlansScreen.kt:456`、`SubScreens.kt:649` 等），金额、账号、手机号、验证码、邮编、日期改走 `SecureNumberField`。

## 4.2 掩码与到期清除

支付密码输入后以圆点回显，不使用 `PasswordVisualTransformation` 之外的额外副本；卡号与安全码由服务端按可见时长下发，客户端在到期时间到达后从内存字典中剔除（`CardsScreen.kt:150-161`、`CardsScreen.kt:635`），界面同步倒计时（`CardsScreen.kt:300`）。

## 4.3 剪贴板

助手消息支持复制（`AssistantScreen.kt:650`）。复制是用户主动行为，客户端不自动写入剪贴板，也不读取剪贴板内容；这一选择牺牲了「粘贴卡号」的便利，但避免了剪贴板被其他应用轮询读取的风险。

# 5 传输与更新

## 5.1 传输

所有银行与助手请求走唯一的 HTTP 实现 `BankHttp.raw`（`HttpTransport.kt:24-80`），默认基址为 HTTPS：

```kotlin
val bankBaseUrl: String = (findProperty("bankBaseUrl") as String?) ?: "https://bank.waveflow.men"
```

（`build.gradle.kts:18`）令牌以 `Authorization: Bearer` 头携带（`HttpTransport.kt:41`），不放在 URL 上，避免出现在日志与代理记录里。

`HttpURLConnection` 走系统 TLS 栈，会校验证书链与域名，但**没有做证书固定**（全仓无 `CertificatePinner`、`X509TrustManager` 自定义实现）。

## 5.2 应用内更新

更新流程为「拉清单 → 比对 versionCode → 下载 → 校验 sha256 → 系统安装器」：

- 清单要求 `apkUrl` 为绝对地址（`UpdateApi.kt:71`）；
- 下载到应用缓存目录（`UpdateApi.kt:93`），校验失败即删除并提示重试（`UpdateApi.kt:118-121`）；
- 安装通过 FileProvider 授权给系统安装器，`FileProvider` 声明为 `exported="false"`（`AndroidManifest.xml:24-30`、`UpdateApi.kt:131`）。

需要说明的是：sha256 只保证「下载到的包与清单声明一致」，清单本身由站点 HTTPS 保护；最终的包来源校验依赖 Android 安装器对同包名签名的比对。客户端**没有**在上层再比一次签名证书，这一点列在 8.5。

# 6 本地数据与运行环境

## 6.1 本地持久化

只有三处持久化，均使用 `MODE_PRIVATE`：

| 文件 | 内容 | 证据 |
| --- | --- | --- |
| `money_meow_session` | 令牌、姓名、手机号、展示名、昵称 | `BankApi.kt:1497-1522` |
| `financial_recovery` | 仅幂等键与操作名，按客户手机号 SHA-256 分槽 | `FinancialRecovery.kt:19,32,48` |
| 读缓存 `ReadCache` | 页面数据，减少重复请求 | `ReadCache.kt` |

`FinancialRecovery` 在注释里写明了它的边界，代码也确实只写两个字段：

```kotlin
/** Only an opaque key and operation label are persisted; no request body or PIN. */
```

（`FinancialRecovery.kt:19`）支付密码不落盘这一点，全仓检索「paymentPassword + prefs/putString」无命中。

## 6.2 日志

全仓 5 处 `android.util.Log`，内容为更新流程的清单地址、版本比对结果与安装 URI（`UpdateApi.kt:51,66,130,132`）以及 dev 变体自动登录失败（`MainActivity.kt:120`）。**没有**输出令牌、密码、卡号或安全码。dev 变体的自动登录只在调试包存在，且失败日志不含凭据。

## 6.3 界面暴露面

- 只有一个 `exported="true"` 的组件：启动用的 `MainActivity`（`AndroidManifest.xml:15-22`），没有对外暴露的 Activity、Service 或深链接入口；
- `FileProvider` 为 `exported="false"`，仅在安装更新时临时授予读权限；
- 权限仅两项：`INTERNET` 与 `REQUEST_INSTALL_PACKAGES`（`AndroidManifest.xml:4-5`），后者是应用内更新所必需。

## 6.4 富文本渲染

助手回复里的公式需要 KaTeX，因此用 WebView 渲染本地生成的 HTML（`MarkdownMessage.kt:36-58`）。该 WebView 开启了 JavaScript，并注册了一个只回传高度的桥接口：

```kotlin
settings.javaScriptEnabled = true
settings.allowFileAccess = true
addJavascriptInterface(object { @JavascriptInterface fun onHeight(px: Int) { heightPx = px } }, "AndroidBridge")
loadDataWithBaseURL("file:///android_asset/", html, "text/html", "utf-8", null)
```

模型输出的正文在拼进 HTML 前统一转义（`MarkdownMessage.kt:241-244` 的 `escape` 覆盖 `&`、`<`、`>`），因此正文里的标签不会被执行；链接由正则在转义后生成 `href`（`MarkdownMessage.kt:237`），**未对 `javascript:` 之类协议做白名单**。这一点的风险与处置见 8.6。

# 7 资金操作安全

安卓侧不重复实现服务端的授权逻辑，但做了两件与服务端配合的事：

1. **一次只允许一笔在途资金操作**。发起前写入不透明幂等键；若已有未核查的记录，直接拒绝并要求先核查上一次结果（`FinancialRecovery.kt:41-50`）。这样即使进程被杀、网络中断，也不会在「结果未知」的状态下重复提交第二笔。
2. **结果未知不猜**。提交失败或超时后不把操作当成成功或失败，而是进入待核查状态，用同一幂等键向服务端查询真实结果（`FinancialRecovery.kt:71` 的 `refresh`）。

敏感操作的最终确认与支付密码校验发生在服务端：客户端把密码随当次请求发送，服务端校验、计错误次数并在连续五次错误后冻结账号。客户端不做「密码是否正确」的本地判断，也无法绕过冻结。

# 8 发现问题与处置建议

风险等级按「影响 × 触发难度」给出。已实现但未验证的部分单独标注。

## 8.1 明文流量开关处于开启（中，已修复）

`AndroidManifest.xml:13` 为 `android:usesCleartextTraffic="true"`，且更新清单允许 `http://` 形式的 `apkUrl`（`UpdateApi.kt:71`）。默认基址是 HTTPS，正常路径不受影响；但一旦出现 http 跳转或配置失误，系统不会拦截明文请求。

**建议**：改为 `usesCleartextTraffic="false"`，仅对本地联调使用的 `-PbankBaseUrl=http://10.0.2.2:8081` 通过独立 debug 清单放开；`UpdateApi` 侧拒绝非 https 的清单与 APK 地址。

**已修复**：主清单改为 `allowBackup="false"`、`usesCleartextTraffic="false"`，并新增 `res/xml/network_security_config.xml` 把 `cleartextTrafficPermitted` 也设为 false，两处同时生效；本地联调由 `src/debug/AndroidManifest.xml` 覆盖，且 debug 的网络配置只对 `10.0.2.2`、`127.0.0.1`、`localhost` 放开明文。`UpdateApi` 在正式包拒绝非 https 的清单与 APK 地址（`UpdateApi.kt:52-56,71`）。

## 8.2 会话令牌明文存储且允许备份（中，已修复）

令牌以明文写入 SharedPreferences（`BankApi.kt:1508-1520`），应用同时声明 `android:allowBackup="true"`（`AndroidManifest.xml:8`）。在已 root 设备或通过 adb 备份，令牌可被取出；令牌未过期即可冒用。

**建议**：改用 `EncryptedSharedPreferences`（AndroidX Security）或由 Keystore 派生密钥加密；`allowBackup` 改为 `false`，或至少通过 `android:fullBackupContent` 排除会话文件。

**已修复**：新增 `TokenVault.kt`，用 Android Keystore 保管的 AES-GCM 密钥加密令牌（每次随机 IV，密钥不出 Keystore），密钥失效时返回 null 并视为未登录。`SessionStore` 改存 `tokenSealed`，读取时优先解密，并自动把旧版本明文 `token` 迁移成密文后删除（`BankApi.kt:1497-1560`）。`allowBackup` 已改 `false`。

## 8.3 卡号与安全码页面未做截屏保护（中，已修复）

`FLAG_SECURE` 目前加在登录页（`AuthScreens.kt:102`）与自绘键盘弹层（`SecureKeypad.kt:104`），而展示完整卡号与 CVV 的页面没有加（`CardsScreen.kt` 全文无 `SecureWindow` 调用）。该页面虽然按秒倒计时隐藏，但倒计时期间可被截屏或录屏。

**建议**：在卡片详情解锁、卡号安全码弹层、以及交易详情等展示敏感字段的页面统一加 `SecureWindow()`。

**已修复**：`CardsScreen` 与 `TxDetailScreen` 在组合开始时调用 `SecureWindow()`，离开页面时由 `DisposableEffect` 撤销（`CardsScreen.kt:63-65`、`TransactionDetailScreen.kt:29-31`）。

## 8.4 登录密码仍走系统输入法（低—中）

登录密码使用带 `password = true` 的普通输入框（`AuthScreens.kt:129-134`），依赖系统键盘与 `PasswordVisualTransformation`。掩码只影响显示，输入法进程仍可读到按键。支付密码已经改走自绘键盘，登录密码没有，原因是登录密码需要字母与符号输入，自绘键盘尚未覆盖字符键盘。

**建议**：要么明确接受「登录密码由系统输入法处理」并依赖服务端风控（当前实际状态），要么后续补一套自绘字符键盘；至少在文档与验收口径里不要宣称「所有密码都不经过系统输入法」。

## 8.5 更新包未在应用内比对签名（低，已修复）

sha256 校验能防传输损坏与清单被替换后的内容不符，但如果攻击者能同时改写清单（例如通过 HTTP 或站点被入侵），sha256 会「对得上」。最终拦截依赖系统安装器对同包名签名的比对，这不是客户端自己的校验。

**建议**：下载完成后用 `PackageManager.getPackageInfo(..., GET_SIGNING_CERTIFICATES)` 比对当前应用与下载包的签名摘要，不一致直接拒绝；同时强制清单走 HTTPS（见 8.1）。

**已修复**：下载完成、sha256 校验通过后再比一次签名证书摘要（`UpdateApi.kt:153-167` 的 `sameSigner`），不一致即删除安装包并提示；取不到签名信息时保守判失败。

## 8.6 WebView 链接协议未做白名单（低，已修复）

正文已转义，`javascript:` 链接仍可能被点击执行（`MarkdownMessage.kt:237`）。WebView 开启了 JS、文件访问，并注册了一个只回传高度的桥接口，攻击面因此受限于「在本地页面里执行脚本、读取 assets」，不足以直接窃取令牌（令牌在 SharedPreferences，不在 WebView 可访问的存储中）。

**建议**：在生成 `href` 时只允许 `https:`、`http:` 与站内相对路径，并为 `WebViewClient` 覆写 `shouldOverrideUrlLoading`，非白名单协议交给系统浏览器或直接拦截。

**已修复**：`isSafeLink` 只放行 `http`/`https` 与相对路径，其余链接退化成纯文本（`MarkdownMessage.kt:239-253`）；`WebViewClient` 覆写 `shouldOverrideUrlLoading`，非白名单协议直接拦截（`MarkdownMessage.kt:45-52`）。

## 8.7 未实现的安全能力（如实标注）

以下能力**当前没有实现**，评审时不应作为已有措施陈述：

- 证书固定（Certificate Pinning）；
- Root / 模拟器检测与完整性校验；
- 界面防截屏的全局开关（目前是逐页添加）；
- 生物识别解锁本地会话；
- 应用锁（后台切回时的二次验证）。

- 未做 WebView 的链接注入实测，8.6 的结论来自代码阅读；
- 未做性能与耗电评估，与本报告范围无关。

# 10 结论与后续

客户端在「输入不经过第三方输入法」「密码页与键盘不被截屏」「结果未知时不重复提交」三件事上是按实际代码落实的，这几项也都在真机上核对过。不足集中在系统配置与存储层面：明文开关、备份开关、令牌加密、敏感页面的截屏保护，都是改动量不大、收益明确的项。

建议的处置顺序：

1. 关闭 `usesCleartextTraffic` 与 `allowBackup`，令牌改用加密存储（8.1、8.2）；
2. 给卡号/安全码等敏感页面统一加 `SecureWindow()`（8.3）；
3. 更新包增加签名比对（8.5）；
4. WebView 链接协议白名单（8.6）；
5. 视资源决定是否补自绘字符键盘（8.4）。

在上述 1—4 项完成前，本报告不认为客户端达到「可对外宣称安全」的状态；当前定位仍是比赛演示客户端。
