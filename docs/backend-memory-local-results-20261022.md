# 后端内存修复：本地双核 / 4GiB / 40GiB 验收

日期：2026-10-22（北京时间）。结论：**本次合成数据与负载下，修复版整套后端在资源上限内通过运行、并发、备份、对账和重启恢复验收。未部署生产服务器。**

## 环境与数据

| 项目 | 实际配置 |
| --- | --- |
| 系统 | 本机 WSL2 Ubuntu 24.04，独立 ext4 数据盘 |
| CPU | cgroup v2，CPUQuota=200%，AllowedCPUs=0,1；`cpu.max=200000 100000` |
| 内存 | 整个测试进程树共享 4GiB；`memory.max=4294967296` |
| Swap | 禁止使用；`memory.swap.max=0` |
| 系统余量模拟 | 测试组内额外常驻分配 512MiB，计入上述 4GiB 上限和峰值 |
| 数据盘 | 40GiB 稀疏磁盘镜像；文件系统可用总容量约 39.1GiB |
| 运行时 | Node 24.14.0，PostgreSQL 16.15，Nginx |
| 业务数据 | 504 户 × 每户 200 笔，共 100,800 笔合成历史流水 |
| 数据格式 | 按真实规范化表和 AES-GCM 字段格式入库；业务 JSON 62,233,482 字节，约 59.35MiB |
| 银行进程堆限制 | 修复前、修复版均为 `--max-old-space-size=512`；这是 V8 old-space 上限，并非整个进程 RSS 上限 |
| Agent 模型 | 本机 OpenAI 流式协议夹具，实际启动 DSH 0.2.1-rc.2 子进程，不调用外部模型 |

同一资源组包含两个银行进程、四个 Agent 父进程、四个真实 DSH 子进程、PostgreSQL、Nginx、压测驱动和系统占用预留。所有进程共用 CPU、内存预算，不能将每个容器分别配置成 4GiB 后声称整机通过。

## 修复前后

| 指标 | 修复前源码快照 | 修复版 |
| --- | --- | --- |
| 银行启动 | 约 28 秒后仍未就绪，SIGABRT 退出 | 约 **450ms** 达到健康就绪 |
| 故障/运行结果 | `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory` | 整套后端、并发、备份、两库对账、银行和 Agent 重启均通过 |
| 单银行进程采样 RSS 峰值 | 约 **800MiB**，随后堆溢出 | 本轮三个银行进程生命周期采样峰值约 **235 / 192 / 108MiB**（含重启进程） |
| 4GiB 资源组峰值 | 约 1.49GiB，V8 堆限制先触发；没有复现内核 OOM | **1,759,600,640 字节，约 1.64GiB**，含 512MiB 系统预留 |
| 内核 OOM 计数 | 0 | `oom=0`、`oom_kill=0`、`max=0` |

旧版对照只启动到银行阶段即失败，没有声称它在本轮复现了昨晚生产服务器的内核 OOM。该实验证明全量档案路径在同一受控堆上限下失败，而修复版可承载整组服务；昨晚实际退出类型仍须原机/云平台日志确认。

## 请求负载

请求交替查询真实银行 HTTP 的账户和分页流水，经 Nginx 转发，轮换 40 个本地测试客户的认证会话。

| 场景 | 时长 | 请求数 | 失败 | P50 | P95 | 最大延迟 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 并发 | 15s | 432 | 0 | 33ms | 50ms | 65ms |
| 5 并发 | 20s | 686 | 0 | 162ms | 180ms | 206ms |
| 20 并发 | 30s | 1,022 | 0 | 636ms | 670ms | 694ms |
| 5 并发持续请求 + 并行 pg_dump | 120s | 3,837 | 0 | 159ms | 184ms | 262ms |
| 合计 | 185s | **5,977** | **0** | — | — | — |

四个 Agent 各建立 30 个会话，共 120 会话；各发送 5 个并发 turn，共 **20 路真实 DSH 对话全部完成**，约 5 秒完成本轮流式模型夹具响应。

并行 `pg_dump` 成功；两库 `reconcileDatabase().ok=true`；银行重启后原认证会话仍能读取账户；Agent 重启后经本人认证重新打开原会话，成功读回已持久化回复。实验盘占用约 **1.62GiB**，包含运行时、合成数据库、日志和备份。

## 功能回归

- PostgreSQL/银行/HTTP/员工/接入/冻结等整合测试：**87 通过、0 失败、0 跳过**。包含跨客户守恒、并发扣款、幂等、失败回滚、旧流水不可改、旧 ID 兼容、懒加载旧档案首次员工查询迁移及 live 闸门。
- Agent 桥接回归：**98 通过、0 失败、2 个可选场景跳过**。跳过项为可选的真实 IM runtime 联调和浏览器绑定流程；不能作为其验收通过。
- Linux 真实 Harness → 银行 HTTP → 确认卡 → SSE 端到端：**ALL PASS**，11 个场景，含产品对比、续费清单、流水核查、定投、历史统计、确认验密转账、错误拒绝、自动重试/停止、付款后回复重试不重复扣款、图片上下文和会话持久化。
- 账户模型文档/业务检查、知识生成、技能检查、接口合约、站内路由检查通过。

端到端模型夹具拆开 role 与正文帧，并等待客户端观察到实时更新，避免依赖固定 100ms 的机器时序；原有流式、鉴权、扣款和保密断言保持。

## 主要改动与边界

机制详见 [内存维护说明](backend-memory-20261022.md)。核心是按需客户投影、对象直读、跳过未变化档案/历史行、增量客户索引、pending 客户扫账，以及 Agent 的回放字节限制、累计快照合并和按需恢复。

本次没有截断流水、删除客户数据或放松金融约束。单客户完整历史仍随该客户档案加载；本轮验证的是上述规模，不代表任意单客户流水规模或无限并发。约三分半的实验不能替代长时间生产监控；云盘 IOPS、真实模型网络、微信通道和长时间语音/附件负载未做同等容量验证。

原始采样与日志位于本地忽略目录 `.generated/backend-memory-lab/`：`fixed-results.json`、`before-results.json`、`resource-final-console.log`、`final-integration-linux.log`、`final-agent-linux.log`、`scoped-final.log`。**最终完整 Linux 门禁退出码为 0，结尾 `ALL PASS`**；事务外写入拒绝的补充回归也通过。Windows 原生 DSH 的流式扩展断言仍有平台差异，本轮服务器结论依据实际通过的 Linux 环境，不将该 Windows 路径作为通过项。随机测试会话凭据只在忽略目录，不进入报告或提交。
