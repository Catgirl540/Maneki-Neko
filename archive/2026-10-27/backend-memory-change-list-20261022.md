# 后端内存修复修改明细

日期：2026-10-22。范围：本次服务器崩溃排查、代码修复及本地容量验证。

本次已完成本地修改和 Linux 模拟验收，尚未部署生产服务器。工作区在排查前已有员工 IM、员工工作台等未提交修改；下表只列本次内存修复新增的内容，不把同文件原有改动计入本次工作。服务器和桥接层修改可与本地保存的修复前源码快照核对。

## 一、银行后端：从全库加载改为按客户加载

| 文件 | 本次修改 | 作用 |
| --- | --- | --- |
| `server/profile-store.mjs`（新增） | 实现 scoped 客户存储：缓存当前客户和业务实际访问的客户，记录原始指纹及待提交修改；提供对象读取、SQL 定位、提交和释放接口 | 避免每个进程启动或每次提交时解密、组装全体客户及全部流水 |
| `server/database.mjs` | 增加 `profileProjection: 'scoped'` 分支，跳过启动时全库 hydrate；接入 scoped 存储 | HTTP 服务启动不再依赖把全部客户档案装入内存；离线兼容模式仍保留 |
| `server/lib/storage.mjs` | 优先使用 `getValue`、`setValuesAtomically` 对象接口；保留旧字符串接口兼容 | 减少客户集合反复 JSON 序列化、反序列化及中间副本 |
| `server/index.mjs` | HTTP 入口显式启用 scoped 模式，数据库连接池上限设为 4 | 让实际银行服务走按需加载路径 |
| `server/bootstrap-postgres.mjs` | 数据库初始化入口启用 scoped 模式，连接池上限设为 2 | 初始化、迁移时也避免无必要的全库档案加载 |
| `server/domain/state.mjs` | 按手机号、客户 ID、账号、卡号和 FPS 查询目标客户；懒加载的档案先完成规范化和兼容迁移 | 只载入本次交易涉及的客户；旧客户首次由收款或员工查询访问时也保持正确账户模型 |
| `server/domain/index.mjs` | 登录、注册、收款人解析、转账、FPS、换手机号等调用改为等待异步客户定位 | 适配按需读取，避免查询尚未完成就继续执行业务 |
| `server/bank-api.mjs` | 在业务事务结束后释放客户投影及业务缓存；初始化演示收款人后释放缓存；相关客户查询改为异步 | 减少请求之间长期保留的客户档案对象 |

目标客户查询中，银行卡先通过 SQL 查询尾号候选，再解密核对完整卡号；不能仅凭尾号把不匹配客户载入并认定为收款人。

## 二、数据库写入：只保存变化，保留账务约束

| 文件 | 本次修改 | 作用 |
| --- | --- | --- |
| `server/database.mjs` | 读取流水时保存原指纹和排序值；保存时跳过未变化客户和历史流水；新流水前插使用更小的 `ordinal` | 余额变化不再触发全部历史流水重写；前插新流水无需平移全部旧行 |
| `server/profile-store.mjs` | 客户绑定索引按本次客户增量维护；修改手机号只移除本人的旧绑定 | 部分客户缓存不会覆盖其他客户的绑定索引 |
| `server/profile-store.mjs` | 先取得 PostgreSQL advisory lock，再读取本次事务快照；提交失败回滚；事务结束释放投影 | 多进程仍按原锁边界读取最新状态，避免使用过期余额 |
| `server/profile-store.mjs` | 拒绝在数据库 unit of work 之外修改、删除或直接 flush scoped 档案 | 防止未归属明确事务的修改滞留缓存，并混入后续客户业务 |
| `server/bank-api.mjs` | 验密失败回滚后，通过新的显式事务保存支付密码错误次数 | 适配严格事务写入，保留错误次数限制 |
| `server/postgres-schema.sql` | 新增 `idx_bank_transactions_pending_owner`、`idx_virtual_cards_active_last4` 两个部分索引 | 加快待处理客户、活动卡尾号的候选查询 |
| `server/database.mjs` | 数据库结构版本从 `2026101502` 升至 `2026102201` | 确保部署前完成对应结构初始化 |

上述优化保留原流水金融身份校验、历史不可删除、借贷平衡及事务原子性。每位客户仍只有一个储蓄资金账户，多币种分别记账，旧余额、冻结和历史流水保留。

## 三、后台扫账与员工查询：避免扫描全部档案

| 文件 | 本次修改 | 作用 |
| --- | --- | --- |
| `server/profile-store.mjs` | 提供待处理客户分页查询，每页最多 25 户；提供员工客户搜索摘要查询 | 由 SQL 找到候选，减少全库解密 |
| `server/bank-api.mjs` | sandbox 扫账按 pending 客户分页，每个客户分别进入原有事务队列；员工搜索使用 SQL 摘要 | 没有 pending 流水时不加载所有客户；搜索不展开全体历史 |
| `server/domain/state.mjs` | 新载入的客户通过统一迁移和规范化入口处理 | 员工直接查询未登录过的旧客户，也能得到合并后的唯一资金账户 |

原有扫账防重复排队逻辑保留；live 模式仍不启用模拟结算。这里按 pending 客户筛选，并未宣称已将加密的到期条件全部下推到 SQL。

## 四、Agent：限制缓存、合并流式快照、按需恢复

| 文件 | 本次修改 | 作用 |
| --- | --- | --- |
| `framework/bridge/session-memory.mjs`（新增） | 同一消息的累计 `assistant-update` 回放只保留最新版本；回放同时限制为最多 256 条、约 1MiB | 避免长回复的多个累计正文副本重复占用内存 |
| 同上 | 中间正文按检查点持久化，首次及后续最多每秒一次；最终正文、工具和业务事件仍持久化；卡密事件不进入持久回放 | 降低高频累计正文写入，保留最终结果及业务事件 |
| `framework/bridge/demo-server.mjs` | 接入上述回放及检查点策略；实时 SSE 仍发送正文更新 | 减少缓存、写入压力，同时保留实时显示 |
| 同上 | 每进程会话缓存上限从 1000 降至 200，每人 50 上限保留；每分钟回收闲置超过 15 分钟且无请求、订阅或运行任务的会话 | 限制长期驻留对象；活跃会话不因空闲回收规则被中断 |
| 同上 | 移除启动时全量恢复中断会话的路径，改为本人认证打开会话时加载，并压缩恢复回放 | 避免进程重启时同时加载大量历史上下文 |
| `framework/bridge/session-store.mjs` | 启动时 SQL 标记中断会话，仅返回 ID；读取回放先取最近最多 256 条，再按累计密文字节约 1.4MB 筛选，至少保留最新一条 | 避免恢复时先取回并解密大量巨型正文快照 |

缓存回收不删除 SQL 会话历史。突然中断时，中间正文回放可能落后一个检查点；不能用会话文字推断银行操作成功与否，账务以银行查询为准。

## 八、验证结论与剩余边界

- 修复前源码在同样的 512MiB V8 old-space 上限、相同合成数据下，约 28 秒后发生 JavaScript heap out of memory，未达到健康就绪；修复版约 450ms 就绪。这证明本地全量加载路径存在内存问题，不能据此断言昨晚生产机一定由 Linux OOM 杀死。
- 修复版完成 5,977 次银行 HTTP 请求，失败为 0；20 并发阶段 P95 约 670ms。整个资源组内存峰值约 1.64GiB，包含 512MiB 预留，内核 OOM 计数为 0。
- 并行备份成功，两库对账通过，银行和 Agent 重启恢复通过；120 个 Agent 会话、20 路真实 DSH 对话完成，模型上游为本机协议夹具。
- Linux 完整门禁通过：银行相关 87 项通过；桥接 98 项通过、2 项可选场景跳过；真实 Harness HTTP 11 个场景 `ALL PASS`。账户模型、知识、技能、接口及路由检查通过。
- 单个客户仍加载该客户完整历史，本次未实现任意单客户历史规模下的恒定内存。约三分半的容量实验也不能替代长期稳定性观察。
- Windows 原生 DSH 流式断言仍有平台差异；本次服务器容量及端到端结论依据通过的 Linux 环境。真实云盘 IOPS、外部模型网络、微信通道及长期语音/附件负载未做同等验收。

部署前须先由数据库所有者运行 `server/bootstrap-postgres.mjs`，使结构达到 `2026102201`；运行时继续使用受限角色和 `BANK_AUTO_MIGRATE=false`。需要保留原加密密钥，并先备份、对账。本次未部署，也未对生产数据做修改。

详细数字及原始日志位置见[本地容量验收报告](backend-memory-local-results-20261022.md)；机制与部署说明见[后端内存维护说明](backend-memory-20261022.md)。
