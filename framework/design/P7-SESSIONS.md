# P7 · 会话管理

> 状态：已实现（网页侧）。
> 相关：`P6-WEB-BRIDGE.md`（演示服务）、`../app/src/lib/agentSessions.ts`（本地存档）、
> `../app/src/lib/useAgentChat.ts`（多会话状态机）。

## 要解决什么

P6 之后客服页只有**一段**对话：点「新对话」把上面那段丢掉，刷新页面全没了。
这在演示里勉强能用，但它同时踩了三个坑：

1. **切走就丢**。想一边等转账回答、一边问别的，做不到——「新对话」会把正在跑的那一段连同上下文一起扔了。
2. **刷新就丢**。浏览器一刷新，刚才问过什么、确认过什么，全没了。
3. **没有"这段对话"这个概念**。所有内容挤在一个数组里，用户没法回头找"上周问过的那个问题"。

## 三条设计决定

### 1. 记录存本地，上下文靠运行时

**决定**：对话列表与内容存在浏览器的 `localStorage`（键 `luckycat.agent.sessions.v1`），
不进服务端。

**为什么**：这一版没有银行后端。agent 演示服务只活在内存里，重启就忘；
把列表放在服务端，重启后要么全空、要么得先做持久化——而真正的持久化该由银行后端来做
（这是 `design/backend-handoff/AGENT-RUNTIME-CONTRACT.md` 里留给后端的事）。
所以两条路各管各的：**记录归浏览器，上下文归运行时**。

**代价**：由此必然产生"记录还在、助手忘了"。这一条不能藏（见第 3 点）。

### 2. 切走不断流，但也不许堆流

**决定**：一段对话在回答时切走，事件流**不关**；等它空闲、而且不是当前打开的那一段时再关。

**为什么**：会话管理最容易做错的地方就是这里。一切走就断流，用户切回来发现回答没了——
而这正是他要会话管理的**原因**。

**但**不能无脑全开：浏览器对同一个源只允许 6 条左右的并发连接，
把每个历史对话的 SSE 都挂着，普通请求会被一起堵死。
所以内存里同时开着的流是压住的：**只有"当前打开的那一段"和"正在回答的那几段"留着**。

判据写在 `closeIfIdle()` 里：`busyRef` 里有它、或者它就是 `activeIdRef` 里那一段，就留着；
否则关掉。切回来时 `openForViewing()` 重新接上——那一段已经空闲，没有事件会错过。

### 3. "失忆"必须写在脸上

**决定**：每段对话记一个 `agentSessionId`（**懒创建**：发第一句话时才建）。
页面打开一段来自磁盘的旧对话时，问一句 `GET /agent-api/sessions/:id`；
如果服务答 `started:false`（建过 ≠ 跑过），就在对话上方写一条红字：

> agent 服务重启过，助手已经不记得这段对话了。上面的记录还在，但你继续说话会从一段新的对话开始。

然后用户真的发言时，换一个新的 `agentSessionId` 重新开始。

**为什么**：不做这一步的话，用户看到的是一段**完整的记录**配一个**答非所问的助手**，
而且界面上**看不出哪里不对**。这是最难排查的一类问题——不是报错，是"它怎么突然变笨了"。

**问不到的时候按"还记得"处理**（`prepare()` 里 `state === null → 'resume'`）：
按"忘了"处理会把一个还在的上下文丢掉，那是不可逆的；按"还记得"处理最坏只是答得不对。

**`GET /agent-api/sessions/:id` 必须是只读的**：顺手把它建出来的话，
每个历史对话都会被问成"还在"，失忆提示永远不会出现，等于没做。
`e2e-consent.sh` 用例 7 就断言这一条：连问三次不存在的会话，服务端会话数不许变。

## 存档的规矩

`agentSessions.ts` 是纯逻辑，不碰 React、不碰网络，所以能直接拿 node 测
（`tools/check-sessions.mjs`）。它管四件事：

| 规矩 | 为什么 |
| --- | --- |
| 读回来逐条校验，坏一条丢一条 | 存档是**用户能改的东西**（localStorage 就在那儿），也可能来自旧版本。一个字段没校验住，表现是整页白屏 |
| 上次中断的"执行中"工具改成"未执行" | 否则下次打开会有一行永远转圈 |
| 最多 50 段 / 总体 2MB，超了从最旧的**整段**丢 | localStorage 写失败是**抛异常**的；不裁的话表现是"历史忽然全没了" |
| 写不进去就丢掉最旧的再试，全不行就清键 | 同上。半截垃圾比没有更糟 |
| 单条超 2 万字截断并**留记号** | 静默截断会让用户以为本来就这么多 |

**不防抖**：一轮对话只产生几条内容，而防抖会在关标签页时丢掉最后一段。

## 已知缺口

**关掉整个页面之后到达的回复不会进本地记录。** 演示服务不重放事件：
SSE 断了就是断了，那一轮的回答只留在服务端的会话日志里，本地不会补上。
切到别的对话不受影响（第 2 点），只有真的关页面或刷新才会碰到。

要补的话有两条路，都留给后端：让服务端提供 `GET /sessions/:id/transcript`
（拿真源覆盖本地），或者在流上补一段时间的事件回放（本地按序号去重）。
两条都比"再存一份记录"更对，但都不该在演示服务里做。
