## 是什么

客服页多了一个「语音」开关，打开后输入框旁多一个**按住说话**的麦克风按钮：
说一句、松开、等回答、听——**一轮一轮**。

**这个开关只管麦克风**。听的那一半不需要先打开它：每条助手回复下面都有播放按钮
（见 `P9-MESSAGE-ACTIONS.md`）。助手回复在开关打开时会被自动念出来，那是
"免手动点一下"的便利，不是唯一入口。

## 三条设计决定

### 1. 按住说话，不做"一直听着"

常开麦克风在银行页面上不能接受：浏览器会一直挂着录音标识，而且会把旁边人的
谈话一起送去转录。所以只有按着的时候才录，松手立刻 `track.stop()`——
不停轨道的话系统的"正在使用麦克风"提示会一直亮着。

状态条是常显的（`正在录音 3 / 60 秒`），不是只把按钮变个颜色：
用户切到别的标签页再回来，必须一眼看出还在不在录。

### 2. 不做全双工，理由不全是工作量

真正的实时要 WebSocket + 流式识别 + 流式合成。这里没做，两个原因：

- **接口形状**：转录端点是"整段音频进、整段文字出"，且**约 60 秒处理上限**。
  所以录音端就卡在 60 秒，而不是让用户说两分钟再报错。
- **场景**：银行客服里"想清楚再按"比"抢话"更合适。抢话式交互会鼓励用户在
  没想清楚的时候就开口，而这里每一句都可能牵出一笔资金操作。

### 3. 说话不能算数

**语音只用来发起，绝不用来确认。** 敏感操作的确认卡片必须手点 + 手输支付密码。
电视里的声音、放一段录音，都能骗过"用语音说同意"——而这正是这道闸门要防的事。

待确认事项出现时，语音会**念一句提醒**（"请在屏幕上核对信息，并输入支付密码。
语音不能代替这一步"），但绝不代答。

## 三件实测过的事（都写成了断言）

语音最容易接错的地方都不会在应用层报错，所以每一条都跑过真实调用：

| 事实 | 怎么验的 |
| --- | --- |
| 合成出来的是**二进制**不是 JSON；拿 `.json()` 去解会得到一段乱码错误 | `e2e-voice.sh` 用例 2 检查响应是 `audio/mpeg` **且文件头是 ID3 或帧同步**（"200 但内容是一段 JSON 错误"是真实存在的失败模式） |
| 格式名完全不存在 → 上游 **400** | `e2e-voice.sh` 用例 4 |
| **写错成另一个存在的名字，上游照样正确转录** | 直接打上游测过：webm 的字节标成 `mp3`，返回结果一模一样（按容器嗅探）。所以"猜格式会得到乱码"这个说法**是错的**，代码注释已按实测改写 |
| `data:` 前缀其实**被容忍**，结果一样 | 同上，直接测过。仍然不带给，但那是因为文档写的是裸 base64——依赖未写明的宽容行为会静默坏掉 |

**还有一条只有中国区才发现的坑**：18 个 TTS 模型里**只有两个有中文音色**
（`qwen/qwen-audio-3.0-tts-plus` / `-flash`），而两个免费的
（`deepgram/flux-tts:free`、`fish-audio/s2.1-pro-free:free`）**都只有英文音色**。
ASR 那边 21 个模型**没有一个是免费的**。所以这个项目的"全免费模型"在语音上不成立，
开了语音就会产生费用——很小，但不是零。

## 边界

- **密钥只在服务端**。浏览器只跟演示服务说话，永远拿不到 OpenRouter 与火山的 key。
  流式那一路的凭据走环境变量（`VOLC_APP_ID` / `VOLC_ACCESS_TOKEN`，或
  `LUCKYCAT_VOLC_APP_ID` / `LUCKYCAT_VOLC_ACCESS_TOKEN` 覆盖），只写在 `~/.zshrc`，
  **仓库里零密钥、日志里零打印**。缺了凭据时 `/tts/stream` 回一条清清楚楚的错误，
  而不是静默没声音。
- **音频不落盘、不留存**。只在内存里过一道就交给上游。银行场景里录音是敏感数据，
  演示服务没有任何理由留着它。转录出来的**文字**会作为用户消息进会话日志——
  那是"用户说了什么"，本来就该在。
- **服务端没开语音时，页面不显示开关**（而不是显示了再报错）。
  `LUCKYCAT_DISABLE_VOICE=1` 可以进入这个状态，用例 7 专门验它。
- 浏览器需要 https 或 localhost；不支持 `MediaRecorder` 时会说清原因。

### 播放时的进度条与波形（2026-09-20 补）

朗读时，**正在念的那条消息**下面会挂一个播放器：波形 + 进度条 + `0:03 / 0:12`。

- **波形是真的**：流式那一路回来的是**裸 PCM**（见下面「流式语音」一节），
  所以采样本来就在手上——`lib/waveform.ts` 的 `peaksFromSamples` 按段取**峰值**、
  按全局最大值归一化即可，**不需要再解码一次**。**不做假波形**——随机画一堆柱子
  看起来一模一样，而它什么也不代表。
  - **波形在整段合成完毕后才算**（用户定的取舍）：边收边算没必要，还会把"播放"
    和"解码"耦在一起。算完才放进状态，此前界面用普通进度条兜着。
  - `check-voice.mjs` 用一个**渐强**的音频来验它：柱子必须右高左低
    （实测左三段均高 5.2、右三段 18.9）。随机画的波形过不了这条。
- **进度条动的是 `transform: scaleX`，不是 `width`**：宽度是布局属性，
  每帧改它会触发重排（`tools/check-motion.mjs` 会拦）。
- **缓存**：`lib/speechCache.ts` 按文本缓存**整段采样 + 波形**。合成是**按字数收费**
  的网络往返，同一句话念两遍没有理由再花一次钱——命中时直接出声，连波形都不用重算。
  - 旧版缓存的是 object URL，于是有一大摊"谁来 revoke、正在播的别回收"。现在缓存采样，
    播放器有自己的缓冲（`streamPlayer.append` 时拷贝进去），**淘汰条目不会打断正在播的声音**，
    那一摊机制整个不需要了。命中也不再在里面合成（`get` 只读、未命中给 `undefined`），
    否则"首帧就播"会被缓存里的整段等待吃掉。
- **不重叠播放**：`speak` 里有 await（合成要几秒），这期间再点一次朗读，
  先前那次回来照样会 `play()`。所以 `useVoice` 里有一个"世代号"，后来者取代先来者；
  加上**整个 hook 只有一个播放器**，两次朗读的采样不可能叠在一起。
  - **说清楚验到哪为止**：6e 用夹具的**帧延迟**造出"第一段还在合成"的窗口，
    断言"播放中峰值采样不超过一段的量（实测 24000，两段会到 48000）"。
    不拖慢的话第二次点击落在已经播起来之后，测不到那个竞态。
| `verify.sh` V5（`LUCKYCAT_E2E=1`） | 上面那条 e2e 会跟着一起跑 |

### 进度条可以点、可以拖、可以用键盘跳（2026-09-20 补）

朗读时进度条是**可操作的跳转条**：点哪儿跳哪儿、按住拖动连续跟随、
键盘 ←/→ 各 5 秒、Home/End 到两端。

| 决定 | 为什么 |
| --- | --- |
| 角色从 `progressbar` 改成 `slider` | `progressbar` 是**只读**语义，读屏软件会念"进度百分之四十"，用户不会想到它能点；加了跳转之后它就是输入控件 |
| 外面套一层 16px 高的壳 | 可见的条只有 3px，**根本点不中**（手指更不可能）；里面那 3px 只负责好看 |
| `touch-none` | 不加的话手机上拖动会变成滚页面 |
| 拖动时去掉过渡动画 | 留着的话手指已经到 80% 了、金色还在 40% 爬 |
| `setPointerCapture` | 手指滑出这条之外还能继续拖，不中途掉线 |
| 时长未知时 `tabindex=-1` | 不知道总共多长就没法"跳到 40%"；与其给一个按了没反应的控件，不如先不放进 Tab 顺序（`aria-disabled=true` 说明原因） |
| 跳转后**立刻**写一次状态 | `timeupdate` 最快 4Hz，不写的话界面会先在旧位置待最多 250ms 再跳过去，看起来像没生效 |

`seek(ratio)` 收的是**比例不是秒**：调用方手上只有比例，秒数要等元数据到了才知道。

门禁 `check-voice.mjs` 的 6g 段通过**真的去点、真的去拖、真的按键**来验：
点 20% / 80%、`aria-valuenow` 跟随、Home、←、End、拖到 15%。
变异（把 `seek` 改成空操作）会让其中 6 条一起失败。

#### 这一节撞出来的两个测试坑

**① 4 秒的音频比 5 秒的键盘步长还短。** ←/→ 永远撞在两端上，
断言测不出"按一下到底走没走"。所以这一段改用 **30 秒**的音频。

**② 语音缓存是按文本做键的、还是模块级的。** 换了 `/tts` 的 route 也没用——
同一个文本直接命中缓存里那段 4 秒的（注释里明明写着这个坑，我自己还是踩了）。
清缓存的唯一干净办法是**整页刷新**。

而刷新又带来两个连带问题，都得处理：

- **`window.__audios` 探针也被清了**（它是 `page.evaluate` 装的），
  于是时长读成 0。现在探针提成了函数，刷新后重装。
- **刷新前钉的那个消息 id 不能用**：每次加载都会给新消息换前缀。
  刷新后重新求值即可。

> **最容易搞错的一处**：`check-voice.mjs` 自己有一个**局部 `login(page)`**，
> 它的职责里包含"清掉本地对话"。6g 里要刷新之后继续用历史，就得调
> **共享的 `loginWithCode`**（只补登录、不碰历史）。调错那个，历史当场被清——
> 表现出来是"刷新之后一条消息都没有"，我为此多查了三轮。

### 「取消」不是「失败」（2026-09-20 修）

用户报的原话：**「我这里闪了一下就没了」**，并且附上了界面上那行红字：

```
朗读失败：The play() request was interrupted because the media was removed from the document.
```

#### 根因

`await element.play()` 还在飞的时候，有人调了 `stopSpeaking()`——`haltAudio()` 会把
`element.src = ''`，那个 promise 就以 `AbortError` 拒绝。而 catch 里**不区分
"被取消"和"真失败"**，于是把一次主动取消报成了错误，还顺手把播放器清掉——
那一下"闪"就是这么来的。

谁会在这时候调 `stopSpeaking()`：点「停止朗读」、点另一条消息的朗读、
**语音模式下自动念下一条**、或者按下麦克风说话。最后一条最常见——
实测里模型一次问候会拆成**两条**助手消息，自动播报先念第一条，第二条一到就把它掐掉。

#### 修法：分辨取消与失败，两半缺一不可

```ts
if (speakSeq.current !== mine) return        // 被取代：新的那次拥有状态
setState('idle'); setSpeakingKey(undefined); setPlayback(undefined)   // ← 必须收拾
if (cause.name === 'AbortError') return      // 取消：收拾干净，但不报错
setError(...)                                // 真失败：必须说出来
```

**中间那行"收拾干净"是补上的第二版**。第一版写成
`if (cause.name === 'AbortError') return` 就完事，结果是：状态卡在
`state='speaking'`，按钮**永远停在「停止朗读」**，用户想再点一次「朗读」都点不出来。
门禁第 ③ 条（"注入的失败移除之后还能正常念"）把这个漏掉的一半抓了出来。

所以「静默」指的是**不报错**，不是**什么都不做**。

#### 门禁怎么写才算数（这一条值得记住）

第一版门禁是去点两次按钮、试着撞进那个竞态窗口。**它抓不住变异**：
把 catch 里那两道判断删掉，断言照样全过。原因写在下面，因为它是个通用教训：

1. 那个窗口取决于**媒体启动的真实时序**（真 MP3 要几十到几百毫秒才开始出声），
   而这一节 mock 的是 4KB 的 WAV，`play()` 几毫秒就 resolve——怎么点都落不进窗口。
2. 试过把 `play()` 的**通知**延后 400ms，**也没用**：真实的 `play()` 早已成功，
   之后清 `src` 不会产生 `AbortError`。延迟通知 ≠ 延迟启动。

**测不到就是测不到**，不该留一条看着像在测的断言。改成直接注入浏览器的两种拒绝、
断言应用的**反应**：

| 注入 | 期望 | 这条挡住的错误修法 |
| --- | --- | --- |
| `AbortError`（媒体被移除） | **不**报错 | —— |
| `NotAllowedError`（自动播放被挡） | **必须**报错 | "干脆把所有错误一起吞掉" |

第二条是关键：没有它，一个 `catch {}` 就能让第一条通过。

#### 根因的另一半：模型爱说过场话

用户那次的直接触发点是：助手先回了一句 **「我查一下。」**（4 个字），
合成出来 **1.008 秒**，播放器活了 918ms——**播放器寿命是对的**，
是内容本身只有一秒。

所以人设里补了第 4 条：**需要调工具时直接调，不要先说「我查一下」「稍等」这类过场话**。
界面上本来就有"正在处理"的转圈，不需要模型再用嘴说一遍。

> 这条改动**连带打挂了三处**（详见 `P11-PERSONA.md` §5）：
> 门禁写死了旧文案、`e2e-voice.sh` 在断言 health 必须夹带模型名、
> `e2e-security.sh` 的探针工具被助手拒绝了。都是"夹具依赖了旧行为"，不是回归。

`check-voice.mjs` 刻意把 `/asr` 用 route 换掉：麦克风是 Chromium 的假设备
（一段固定音调），**接线**和**识别**混在一起测的结果是两个都不稳。
真音频的往返交给 `e2e-voice.sh`。

> **夹具的转录文案必须是一句不触发敏感工具的话**（现在是 `TRANSCRIPT = '你好呀'`）。
> 原来写的是「帮我看看上个月的账单明细」——那条会触发查流水的敏感操作，
> 运行时弹确认卡片把工具挂住，助手在等确认期间**不产出任何文本**，
> 于是"等助手答一句"一直等到超时、后面关于朗读的断言全挂。
> 以前没暴露，是因为模型在调工具前会先说「我查一下。」——那句过场话恰好成了"助手回复"；
> 人设加了第 4 条之后，这个夹具就站不住了。

> **另一个夹具坑**：`messageRows.last()` 是**活定位器**。这一轮里助手可能说两条
> （实测一次问候被拆成两条），后到的那条一出现，`last()` 指向的就换了人——
> "同一段文字念第二次不该再合成"会去合成**另一句话**，次数从 1 涨到 2，
> 看起来像缓存坏了。失败信息里那两句不同的话就是证据。
> 现在先等助手条数稳定，再取出 `data-message-id` 钉死。

## 流式语音：不等整段合成完（2026-09-20 补）

### 要解决的问题

整段合成（`/agent-api/tts`）是**一次性**的：服务端把整段话合成完才回音频。
十几二十个字的回复实测要 **2~3 秒**，长一点的更久——按钮点下去到出声之间是一段
没有反馈的空白期。

流式这条路把这段空白压到**首帧的时间**：上游合成出第一帧就推过来，浏览器收到就播，
后面的帧在"正在播前一段"的时间里陆续到。

### 走过的岔路：先想的是"逐句合成"

第一个方案是把回复按标点切成句子、每句单独合成、播完一句接下一句（做了切句器
`streamSpeech.ts` 与它的门禁）。它能把首音提前，但有两个天生的毛病：

- **句与句的衔接**不如整段合成自然（每句的韵律是各自生成的）；
- 切句规则本身是一堆取舍（短句要不要按住合并、长句在哪儿断开、英文句号算不算），
  每一个取舍都要单独测。

用户的方向更直接：**用支持流式输出的模型**。既然上游能流式吐音频，就不需要自己切句
——把整段文字交给它，它自己按子句合成、一帧一帧返回（350/351 事件就是它的子句边界）。
所以切句器与 `check-stream-voice.mjs` **已删除**（不留死代码）。

### 链路

```
浏览器                       演示服务（bridge）                  火山引擎语音技术
  │  POST /agent-api/tts/stream      │                                  │
  ├─────────────────────────────────►│  WebSocket（单向流式）           │
  │                                  ├─────────────────────────────────►│
  │  SSE: start / audio×N / end      │  ◄── 352 帧（裸 PCM16 LE）        │
  │◄─────────────────────────────────┤                                  │
  │  onAudio → streamPlayer.append   │                                  │
  │  → Web Audio 排片出声            │                                  │
```

- **桥接**：`bridge/volc-stream.mjs` 是协议层（组帧/解帧/流式助手），
  `demo-server.mjs` 只做 SSE 转发。密钥只在服务端。
- **前端**：`api/agent.ts` 的 `synthesizeSpeechStream` 解 SSE；
  `lib/streamPlayer.ts` 用 **Web Audio** 分帧播放；`lib/pcm.ts` 解 PCM；
  `lib/useVoice.ts` 把三者编排起来（含取消/失败/缓存）。

### 上游协议（都是实测对准的，不是照抄文档）

| 事实 | 怎么确认的 |
| --- | --- |
| 端点 `wss://openspeech.bytedance.com/api/v3/tts/unidirectional/stream`，旧版控制台鉴权（`X-Api-App-Id` + `X-Api-Access-Key`），资源 `X-Api-Resource-Id: seed-tts-2.0` | `framework/scripts/probe-volc-stream.mjs` 真连过 |
| `req_params.additions` 必须是 **JSON 字符串**，给对象会被拒：`json: cannot unmarshal object into … additions of type string` | 探针实测报错原文 |
| **资源 id 与音色必须同代**：`seed-tts-2.0` 配 `zh_female_cancan_mars_bigtts` 报 `resource ID is mismatched with speaker related resource`；换 `zh_female_xiaohe_uranus_bigtts` 通过 | 探针实测（1.0 资源 `seed-tts-1.0` 在这个账号上直接 403） |
| **352 音频帧是裸二进制 PCM16 LE**，不是 JSON（`byte2=0x00` 表示 raw 序列化）。文档的 payload 参数表写的是"二进制数据包"，但"按 JSON 读 `audio_binary`"会一个字都取不到 | 探针把帧 hex 打出来对齐的 |
| 事件流：350（子句开始，JSON 带 text）→ N×352 → 351（子句结束）→ 152（会话结束，带 `usage`）→ 52（连接结束） | 同上 |
| 收尾要发 FinishConnection（事件 2）再关；服务端也可能抢先关连接——**两种情况都算成功** | 第一次实现把"抢先关闭"当成了失败（探针直接抛出 `code=1000`） |
| 26 个字 → 12 帧 → 210446 字节 ≈ 4.4 秒音频；每帧约 0.25~0.5 秒 | 探针统计 |

`tools/check-volc-frame.mjs` 把上面这些帧格式**离线钉死**（15 条）：组帧的 header/JSON、
raw 不当 JSON 读、短帧不抛异常、错误帧的 error 文本可读。协议层不联网也能验。

### SSE 契约（未来真实后端按这个实现）

请求 `POST /agent-api/tts/stream`，体 `{ text, voice? }`（`text` 上限同整段合成，600 字截断）。
响应 `text/event-stream`：

| 事件 | data | 说明 |
| --- | --- | --- |
| `start` | `{ "format": "pcm", "sampleRate": 24000 }` | **必须先发**：播放器要按它建缓冲 |
| `audio` | 一帧裸 PCM16 LE 的 **base64** | 一帧一个事件，顺序即播放顺序 |
| `sentence` | `{ "type": "start"\|"end", "text": "…" }` | 子句边界（现在只用于日志与未来字幕，浏览器可以忽略） |
| `end` | `{ "frames": N, "bytes": M, "truncated": false }` | 整段合成完毕 |
| `error` | `{ "message": "…" }` | 上游失败；**必须**由界面报出来 |

文本截断沿用整段合成那条规矩（按字数计费，长回复也念不完）：`end.truncated` 说明截断了。
浏览器断开时桥接会 abort 上游请求——没人听的合成不该继续烧钱。

### 播放模型（`lib/streamPlayer.ts`）

- **尾巴排片（tail scheduling）**：每个新到的帧立刻排一个 `AudioBufferSourceNode`，
  起点是上一段结束的时刻，帧与帧无缝；音频来得比播放慢（网络卡了）就从"现在"起排，
  接受一个小停顿。`AudioBufferSourceNode` 会按缓冲区的采样率自动重采样到上下文采样率。
- **为什么不用 `<audio>` + MediaSource**：流式给的是裸 PCM，MediaSource 对它支持很差
  （`audio/pcm;codecs=…` 各浏览器不一）；Web Audio 天生就是吃采样的。
- **`markComplete()` 是"播完了"判据的一半**（见下面的 bug 记录）。
- **`seek` 只能跳到已经收到的采样范围内**：没到的地方没有数据，这是流式播放的物理限制，
  不是实现偷懒。进度条的 `aria-valuemax` 因此是"已缓冲时长"，随帧增长。
- **波形在整段合成完毕后一次算完**（用户定的），播放期间只走普通进度条。
- **诊断口 `window.__voicePlay`**：沿用 `window.__audios` / `window.__voiceLogs` 的老规矩，
  门禁从页面外读"在不在响、位置、已收采样、世代号"。

### 这一节撞出来的三个真 bug（都是门禁抓的，不是看出来的）

| bug | 症状 | 根因 |
| --- | --- | --- |
| **播放器以为"第一帧播完=整段念完"** | 真机上会"只念出第一小段就停" | "播完了"的判据是"已缓冲的采样都排过片了"——第一帧一到就成立。改成必须由调用方在**流结束**时 `markComplete()`，判据是 `complete && 位置≥时长` |
| **`stop()` 没把位置归零** | `End` 念完之后再点朗读，播放器一闪就收、起不来 | `stop()` 清了采样、却没清 `playedBase`；下一次起播从"上一段末尾"开始排片，那里已经没有音频 |
| **catch 里先收拾、再判"是不是取消"** | 上游明明报了错，界面一句话都没有 | `teardownPlayback()` 会 abort 那个 controller，之后再读 `signal.aborted` 永远是 true——真失败被误判成"用户取消"。改成**先记下 `wasAborted` 再收拾** |

前两个是"流式特有"的（只在帧慢慢到的时候才暴露），第三个是编排顺序的错。
它们都**不会在整段合成的老路径上出现**——这就是为什么必须有一条"帧慢慢到"的门禁。

### 门禁怎么造"帧慢慢到"

Playwright 的 `route.fulfill` 是**把整段响应一次交出去**的——用它测不出"不等全文就出声"
（那正是这个功能的意义）。所以 `tools/lib/ttsFixture.mjs` 起一个**真的 HTTP 服务**，
一帧一帧、可延迟地写 SSE，门禁用 `route.continue` 把 `/agent-api/tts/stream` 接到它上。
URL 参数就是夹具的模式：`seconds`（音频多长）、`delay`（每帧延迟）、`mode=error`（直接报错）、
`errorAfter=N`（发到第 N 帧后中断）。

核心断言只有一句：**进入播放状态时，那次请求还没结束**。

```
PASS  音频还没合成完就已经在响了（流还没结束=true，已播 0.21s、已收采样 4800）
       ——这就是"流式"：不等整段 TTS
```

变异验证：把 `speak` 改成"等整段合成完再播"（流式的反面），这条必挂；
把缓存写入删掉，6d 的"同一段文字念第二次没有重新合成"必挂。两条都实测跑过。

### 语音门禁不再依赖模型回复

原来 6b 之后要等模型答一句（最长等 90 秒）。实测撞到上游抖动：**16 PASS / 3 FAIL**，
而且因为拿不到助手消息，后面点按钮的断言直接抛异常、整份门禁崩掉。

现在改成**预置一条确定的助手消息**：用应用自己的存档格式
（`localStorage['luckycat.agent.sessions.v1']`，见 `lib/agentSessions.ts`）写进去，
刷新后它就是一个普通的助手气泡，朗读按钮照常工作。于是这一段：

- **确定性**：文本与音频都由夹具给定，不受模型回什么、什么时候回影响；
- **零成本**：不再为门禁付模型钱（真合成的往返仍由第 4 节与 `e2e-voice.sh` 覆盖）；
- **不再因为上游抖动闪失败**。

真实模型对话是 `check-agent` 与 `e2e-consent.sh` 的事，不该由语音门禁兼职。
