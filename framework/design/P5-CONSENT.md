# P5 · 敏感操作闸门（展示 → 确认 → 身份验证 → 才执行）

## 1. 要求

> 如果涉及到交易、敏感信息查看，需要展示交易的信息，用户确认、身份验证时候才能执行。

一句话：**没经过"看一眼 + 点确认 + 验身份"的操作，不许执行**。这不是提示词层面的礼貌，
而是运行时层面的拦截。

## 2. 为什么这套机制是"真拦截"

`framework/packages/consent/` 挂在 DSH 自己的工具流水线上：

```
tools/pre-execute  →  审批 ask  →  单调守卫  →  执行 / 不执行
        ↑                 ↑
   返回 {kind:'ask'}   ctx.approval.request() → approval/request 瀑布 → 我们的答复者
```

三条上游保证（都不是我们写的，是 DSH 内核行为）：

1. `ask` 之后，只有答复者返回 `allowed-once` 才会执行；**没有任何答复者时一律拒绝**。
2. 批准是**一次性**的（`allowed-once`），不会复用。
3. `ctx.tools.guard()` 是单调的：后面的监听者只能继续收紧，不能把拒绝改回允许。

所以"漏一次确认就放行"这条路在内核层就不存在。我们做的是**把 ask 接上人**。

## 3. 分层

| 层 | 包 | 内容 |
| --- | --- | --- |
| 通用框架层 | `@luckycat/dsh-consent` | 服务 `ctx.consent`、挑战生成/判定、HTTP 长轮询通道。**不含任何银行业务规则** |
| 示例消费者层 | `@luckycat/dsh-bank-demo` | 8 个占位业务工具 + 规则表（哪些操作要确认、要不要验密码、展示哪些字段） |

规则表在消费者侧，是因为"哪些操作敏感、要不要验密码"是**业务决定**，
会随业务变化；通用层只提供机制。真实银行后端应自建同等插件。

## 4. 判定矩阵（全部 fail-closed）

| 情况 | 结果 |
| --- | --- |
| 同意 + 验证通过 + challengeId 一致 + 未过期 | **放行**（`allowed-once`） |
| 用户点取消 | 拒绝，工具体不运行 |
| 需要验证，但答复里没有 `verified: true` | 拒绝 |
| 验证方式不符（例如用短信码顶替支付密码） | 拒绝 |
| `challengeId` 对不上（重放旧答复） | 拒绝 |
| 已过有效期 | 拒绝 |
| 通道连不上 / 返回看不懂 / 超时 | 拒绝 |
| 会话被中断 | 拒绝 |
| 展示信息生成失败（`describe` 抛异常） | 拒绝 |
| 工具没被声明为敏感操作 | 交给下一个答复者，不影响别的流程 |

判定逻辑在 `challenge.ts` 的 `judge()` 里，是**纯函数**，11 条分支全部有离线单测。

## 5. 展示的信息从哪来

`SensitiveOperationSpec.describe(args)` —— 由消费者插件提供的**纯函数**，
把工具参数变成「标签 / 值」列表。它同时用于两处，且必须是同一份：

- 送给通道（网页上的确认卡片逐条渲染）；
- 拼进审批的 `reason`（进会话日志的 `approval/asked`，也是模型在等待期间看到的那句）。

**为什么要同源**：模型会据此向用户复述。如果模型自己编一份"转账给某人 800 元"，
而卡片上写的是别的金额，用户确认的就是一份被篡改过的信息。

## 6. 身份验证：密码不进 agent

- 网页把支付密码 POST 给**确认服务**（演示环境是 `bridge/demo-server.mjs`，代替银行后端）；
- 确认服务校验后，只把一张 `{method, verified, ticket}` 的**结论**回给 agent；
- agent 进程、模型上下文、会话日志里都**没有**密码。

e2e 里有一条断言专门盯这件事：会话日志中不得出现支付密码。

真实部署时，短信验证码网关、人脸核身这类验证方式由后端实现；框架只声明"需要哪种方式"
（`verification: 'payment-password' | 'sms' | 'face'`）。

## 7. 审计

上游的审批服务会自动在会话日志里落一对事件：

- `approval/asked`：`{ id, toolName, callId, reason }`，`reason` 就是我们渲染的那份展示信息；
- `approval/decided`：`{ id, outcome }`。

e2e 断言这一对**成对出现**且 id 相同、`outcome === 'allowed-once'`。
日志是只读审计记录，模型看不到它，它也不会改写。

## 8. 实测踩到的坑（都留了注释，别再踩）

1. **插件导出形态不能混用**。`@luckycat/dsh-consent` 一开始同时写了
   `export default ConsentService` 和 `export function apply`。DSH 的 Loader 一旦看到
   default export，就会把函数插件的命名空间（`name`/`inject`/`Config`/`apply`）整体丢掉
   ——服务能读到、规则表有 8 条，但**监听器一个都没挂上，工具照常执行**。
   现象极具迷惑性：一切"看起来都在"。参见 `packages/AGENTS.md` 的 Plugin exports 与
   `docs/postmortem/0001`。
2. **长轮询的"对端断开"要听 `res`，不能听 `req`**。请求体读完之后 `req` 的 `close`
   早就发过了（Node 的语义是"请求流结束"，不是"对端断了"），挂在 `req` 上的清理永远不触发。
   后果：agent 已放弃等待，网页上的卡片还在，用户点"确认"拿到 200 却什么都不会发生。
   正确做法是听 `res` 的 `close`，用 `writableEnded` 区分"正常回完"与"对端断了"。
3. **模型会用嘴确认**。加人设之前，模型收到"帮我转 800 元"会先回一句
   "请问您确认要执行这笔转账吗？"然后**不调用工具**，确认流程永远不触发。
   现在 `personaSuffix` 里明确写了"不要用文字征求确认，直接调用工具，
   运行时会弹确认卡片"。这是"确认由谁负责"的边界问题：模型负责发起，运行时负责确认。

## 9. 已验证 / 未验证

**已验证（`bash scripts/e2e-consent.sh`，需联网）**

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | 转账 | 确认前工具体未执行；挑战含收款人/金额/尾号且要求支付密码；确认+正确密码后执行；审计事件成对且 `allowed-once`；支付密码不在日志里 |
| 2 | 取消 | 工具体未执行 |
| 3 | 密码错 | HTTP 401，工具体未执行（且允许重试） |
| 4 | 不回答 | 超时后工具体未执行，卡片被清理 |
| 5 | 只读查询 | 有确认、不要求密码、返回占位余额 |
| 6 | 重复答复 | 第二次答复 404；回执号唯一（只执行一次） |

另有 56 条离线断言（`scripts/verify.sh`）与 101 个离线单测。
网页侧 14 条断言见 `tools/check-agent.mjs`。

**未验证 / 未做**

- 短信验证码与人脸核身：框架声明了这两种方式，演示服务只实现了支付密码，
  真实验证要等后端（现在遇到这两种会返回 501 并拒绝，不会静默放行）。
- 会话取消（abort）接口：上游 SDK 协议没有这个方法，暂不做。
- 多用户并发：演示服务是一个进程带多个会话，没有做租户隔离；生产由后端负责。
- `compaction` 触发（此前已标记未验证，本次未涉及）。
