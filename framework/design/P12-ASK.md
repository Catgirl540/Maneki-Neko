# P12 · 模型问用户：提问卡片

> 需求原文：「如果 ai 需要向用户问问题才能操作，需要调用问问题工具，弹出一个卡片，
> 用若干选项或者输入自己的答案，可以单选也可以多选」。
>
> 结论：**官方本来就有这套工具**（`ask_user_question`），做的是把它挂起来 +
> 写一个答复者 + 网页卡片。但过程中发现「挂起来」这件事有个**安全洞**必须自己补。

---

## 0. 结论

| | |
| --- | --- |
| 模型用的工具 | 官方的 `ask_user_question`（`@deepseek-ai/dsh-tool-ask-user`） |
| 参数形状 | `questions[]`，每题有 `id` / `question` / `header?` / `options[{label,description?}]` / `multi_select?` |
| 答复形状 | `{ answers: [{ id, selected: [], custom? }] }` |
| 三种答法 | 单选（radio）、多选（checkbox）、自由输入（常驻输入框） |
| 网页卡片 | `app/src/components/agent/QuestionCard.tsx` |
| 答复者 | **我们自己写的** `framework/packages/ask/`（官方只在 DSH 自带 Web GUI 里实现过） |
| 门禁 | `tools/check-ask.mjs`（39 项，四段），两次变异测试各精确命中 |
| 硬性安全性质 | **不许用提问框索要凭据**（代码拦，不靠人设） |

## 1. 官方有三层，我们只缺中间那层

```
模型 ──调用──▶ ask_user_question            官方：@deepseek-ai/dsh-tool-ask-user
                     │
                     ▼
              ctx.userQuestions.ask()        官方：@deepseek-ai/dsh-user-questions（服务定义）
                     │
                     ▼
        user-questions/request waterfall      ← 这里要有人"回答"
                     │
                     ▼
              ❌ 官方只有 DSH 自带 Web GUI 的实现（@deepseek-ai/dsh-client-ui-user-questions）
                 我们用的是自己的银行网页 → **必须自己写答复者**
```

所以本包做三件事：

1. 把官方的**服务**与**工具**两行插进组合树（`cordis.patch.yml`）；
2. 写答复者 `luckycat-ask`：把问题 POST 给桥接、等答复、回填；
3. 桥接侧长轮询 + SSE 推卡片，网页侧渲染 `QuestionCard`。

**为什么这又是"套一层壳"**：官方的 `dsh-user-questions` / `dsh-tool-ask-user`
都不声明 `dsh.bundle`，`dsh plugin add` 挂不上；但从**我们自己的 bundle 补丁**里
插 `- id/name` 是可以的。这和 `packages/tool-fs` 挂 fs 那几个包是同一个手法
（见 `P10-IMAGE.md` §2）。

通道形状**刻意与确认通道同形**（`POST` 挂住 → SSE 推 → 用户答 → 原路返回），
因为已经有 `e2e-consent` 把那条路踩熟了。但两者是**两个插件**：

| | 确认闸门（`luckycat-consent`） | 提问（`luckycat-ask`） |
| --- | --- | --- |
| 管什么 | **这个操作能不能执行** | **收集信息** |
| 挂在哪 | `tools/pre-execute` + `approval/request` | `user-questions/request` |
| 答不上来 | fail-closed：工具**不执行** | 模型拿不到信息，但没有任何东西被"放行" |
| 要验身份吗 | 要（支付密码） | 不要——用户点个选项不需要验身份 |
| 票据 | 有（只含"已验证"，不含密码） | 没有 |

合成一个插件会让"哪些操作必须确认"和"模型能不能提问"互相牵连，所以分开。
代价是 HTTP 通道那段各写了一份（各约 60 行）——两边载荷与安全语义不同，硬合并更难读。

## 2. 必须自己补的安全洞：不许用提问框索要凭据

`ask_user_question` 弹出的是一个**用户会当真的输入框**。它长得和银行的正常表单一样，
用户没有理由怀疑。所以只要模型问一句「请把您的支付密码填在这里」，
就有一个看起来很正规的框在等他把密码打进去。

**人设里当然也写了不许问。但人设是软的**——这一轮做"隐藏模型名"时已经实测过一次：
界面上藏得再好，问一句模型就自己说了（见 `P11-PERSONA.md` §2）。
凭据这件事的后果是丢钱，所以放在**代码里拦**：`packages/ask/src/guard.ts`。

### 规则：凭据词 + 索要动词 + 没有否定

三个条件都满足才算"索要"。为什么要三个：

| 只查凭据词 | 会把银行最该说的话拦掉：「请不要把密码告诉任何人」 |
| --- | --- |
| 只查索要动词 | 会把「请输入转账金额」拦掉 |
| 两个都查、**不看否定** | 还是会把上面第一句拦掉——`告诉` 也是索要动词 |

**第三个条件是实测补上的**：第一版只查前两个，我自己的门禁 B2 立刻报了两条误拦。
改成按标点**分句**、每句独立判、句内有否定词就跳过之后才过。

分句是必需的：「请不要把密码告诉任何人，**请在这里输入**您的密码」——
前半句否定、后半句索要，切不开就判错。

### 已知局限（不假装更强）

- 用否定词包装的真索要（「请勿忘记输入您的密码」）会漏过去。
  这是启发式，不是语义理解。
- 真正的保证在别处：凭据验证走的是确认闸门那条"展示 → 确认 → 验身份"的路，
  而且**支付密码只到服务端，从不经过模型**（见 `P5-CONSENT.md`）。
  这里是多加一道，不是唯一一道。

### 被故意放过的边界

**选项标签里单提凭据词，不拦。** 例如选项是「银行卡号后四位」——
那是实测里模型真的给过的一个选项（用来确认收款账户），**正常且有用**。
用户点它只是把这几个字回给模型，不会交出密码。按"见到凭据词就拦"写，
会把这条正常路径一起拦掉。门禁 B3 把这条边界钉住了。

## 3. 一次问答的完整时序

```
模型调 ask_user_question({questions:[…]})
   ↓
官方 tool-ask-user → ctx.userQuestions.ask() → waterfall
   ↓
luckycat-ask：① parseQuestions 校验形状（题数 ≤10、选项 ≤20、id 不重复）
              ② assertQuestionsAllowed 防钓鱼守卫   ← 拦在这里，卡片根本不会出现
              ③ POST /agent-api/questions（带 sessionId）
   ↓
桥接：查形状 → 生成 questionId → publish SSE {type:'question'} → **HTTP 请求挂住**
   ↓
网页：QuestionCard 渲染 → 用户选/填 → POST /questions/:id/answer
   ↓
桥接：校验（id 问过、单选不超一个、每题有实质答复）→ resolve 被挂住的那个请求
   ↓
luckycat-ask：parseAnswer 再校验一遍（id 问过、选项是给过的、每题都答了）
   ↓
工具返回 {answers:[…]} → 模型拿到工具结果，接着往下走
```

**两侧都校验是刻意的**：这条链上任何一侧单独失守，都不该让一个畸形或骗人的卡片
出现在用户面前。两侧的职责划分：

| 位置 | 管什么 |
| --- | --- |
| 桥接 | **形状**：id 问过没有、单选有没有超、有没有空答复、题数上限 |
| 插件 | **语义**：选项是不是给过的、题目有没有索要凭据、答复能不能对上题目 |

## 4. 实测踩到的四处

### ① 空答复被当成有效答复结算掉了（真 bug）

桥接原本只查"每道题的 id 都在"，不查"答了没有"。于是 `custom: "   "`（纯空白）
会被**接受并结算**：问题关闭、模型收到一份什么都没说的答案、用户在界面上
可能只是觉得"提交没反应"。

更直接的后果：**紧跟在后面的那次正常答复会拿到 404**——问题已经被空白答复消费了。
门禁 A4/A5 同时红就是这样暴露的。

### ② 门禁自己的三处假失败

| 断言 | 我错在哪 |
| --- | --- |
| A6 推了 `question-resolved` | 查得太急。服务端先 publish 再 resolve，但读 SSE 的是另一条异步循环，那一刻那一帧可能刚写进 socket |
| C2b 答案回到模型 | nonce 只写给了"下标 > 0 的题"。模型这次只问了 1 道题 → token 根本没进答案 |
| C3 模型继续往下走 | ①快照取在 C2b 等待**之后**，把等待期间的事件算成了"旧的"；②改完之后又把等待循环删了，于是永远等不到 |

C3 的断言口径本身也改过一次：原本断言"这一轮结束（idle）"，但模型答完第一张卡
**会再问一张**（补充信息），那时它既没 idle 也没卡死——那正是这个功能该有的样子。
现在断言的是"**有进展**"：新问题 / 新工具调用 / 新助手消息 / 真的结束，四者之一都算。

### ③ 规则要求"凭据词 + 索要动词"，我的断言却假设"只看凭据词"

见 §2 的"被故意放过的边界"。

### ④ 人设没写"可以提问"，模型就在正文里问

第一版人设只列了"能办的事"，没提提问。于是模型缺信息时**在正文里问一句然后停下**
——用户只能再打一遍字，而它那一轮白跑了。**那正是这个需求要解决的问题。**

补了第 3 条硬规矩之后才变成"弹卡片"。这条和原有的第 1 条（不要用嘴确认）
是同一条道理：**该用工具的时候就用工具，不要用嘴。**

## 5. 门禁：`tools/check-ask.mjs`（39 项）

```
node tools/check-ask.mjs
```

| 段 | 内容 |
| --- | --- |
| **A** 服务端协议（确定性） | 卡片推送、答复回填、空答复/漏答/没问过的 id/重复答复/放弃等待后答复 → 400/404 |
| **B** 防钓鱼守卫（离线，直接测构建产物） | 5 条必须拦、4 条必须不误拦、选项掩护下索要要拦、追加规则生效、非法正则加载期报错 |
| **C** 真模型（联网） | 模型真的弹卡片；我们填的 nonce 出现在 `ask_user_question` 的**工具结果**里；答完继续往下走 |
| **D** 界面（浏览器） | 卡片弹出、单选渲染 radio、多选渲染 checkbox、纯自由输入题没有选项、未答完禁用提交、答完提交、答案原样到达、卡片收起 |

### 为什么 A 段和 D 段要"自己造一道题"

模型给什么题是它自己决定的——这次给单选、下次给多选、再下次只问一道。
**靠模型来覆盖单选/多选/自由输入三条路，断言就会变成看运气。**

所以 A 段与 D 段自己构造一道包含三种问法的问询（`THREE_WAY`）直接打进桥接：
单选 2 个选项 + 多选 3 个选项 + 一道纯自由输入题。C 段才去验"模型会不会用"。

D 段拿页面正在用的 `sessionId` 的办法：监听 Playwright 的 `page.on('request')`，
从页面自己发的 `/agent-api/sessions/<id>/stream` 请求 URL 里取。
用的全是生产端点，不加测试专用接口。

### 变异测试

| 注入的变异 | 预期 | 实测 |
| --- | --- | --- |
| 守卫 `looksLikeCredentialRequest` 永远返回 false | B1 与 B3b 失败 | ✅ B1 ×5 + B3b 失败；**B2 照常通过**（它本来就在断言"不拦"） |
| `QuestionCard` 把多选也渲染成 radio | D3 失败 | ✅ 只有 D3 失败（D7 仍过——它验的是数据，不是控件类型） |

另外 A4/A5 的那次失败**不是人造变异**，是真实 bug 先被门禁抓到（见 §4①）。

## 6. 还没做 / 没验的

- **`user-questions/request` 上只有我们一个答复者**。如果哪天同时挂了两个
  （例如也挂上官方 Web GUI 那套），谁先返回谁赢，`next()` 的委派顺序没有测过。
- **一次多题是一个卡片一起提交**，不是官方 Web GUI 那种一题一屏的向导。
  题多的时候（实测模型一次问过 5 道）卡片会比较长。
- **超时值是两道独立的闸**（插件 180s / 桥接 180s），但没有测过"插件先超时"
  和"桥接先超时"分别是什么观感——只测了"插件放弃后答复拿 404"。
- **自由输入没有任何内容过滤**：用户可以在输入框里打任何东西，
  这段字会原样进模型上下文。提示注入的面上没有额外防护。
- **防钓鱼守卫只查中文与少量英文**。其他语言的索要（日语、韩语……）会漏。
- **模型的自问自答**：没有测过"模型问完自己又替用户答"这种情况
  （理论上答复只能来自通道，模型碰不到）。
